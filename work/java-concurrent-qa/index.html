多线程

Q：什么是JMM？什么是原子性可见性有序性？哪些对象相对是共享变量？
A：

JMM，Java Memory Model，Java内存模型。主要是为了解决多线程同步和通信的可见性、原子性、有序性问题产生的。

具体来说什么是JMM呢：可以参考这张图 ((20260430104747-kl872fu ‘image ‘))，在内存中每个线程有自己的VM栈，同时也会有共享变量区域（这块区域叫主存），多线程需要访问共享变量时需要将主存中的共享变量复制一份到本地内存中，本地修改后过一段时间才会同步到主存中。

什么是可见性、原子性和有序性？

  1. 可见性：线程A修改完共享变量后不一定马上同步到主存中，需要过一段时间才能同步。线程B不能马上看到这个变量被修改了。

  2. 原子性：一个经典例子「i++」，分三步操作 1、读i； 2、i加1； 3、赋值。多线程对i这个变量进行操作的时候，就会出现原子性问题。

  3. 有序性：有时候编译器和CPU为了提高速度，会在不影响单线程结果的情况下进行指令重排，总体遵循happens-before规则。一个经典的例子就是「Obj a = new Obj()」

    下面的123操作有时候会改成132, 在多线程进行的情况下可能会导致错误：a指向地址没有赋值，没有实际对象。

    1. 开辟对象的内存空间
    2. 内存空间赋初始值
    3. 修改a的引用到指定内存空间

哪些对象是共享变量？

  • JVM堆/元空间（方法区）的非线程私有的对象是共享变量。

  • 可以被多线程共享的变量是共享变量。比如

    • public class A{
    int i = 1; // 这里的i 就是堆A对象的属性，属于共享变量。
    method1(); // 修改i
    method2(); // 修改i
}
Q：Java的线程实现？虚拟线程和平台线程？切换和调度是否由内核态实现？和go中的协程呢？虚拟线程和平台线程的作用是什么？
A：

Java中的线程实现，JDK21之前使用传统的1:1封装内核线程，JDK21之后引入显式的虚拟线程，M:N封装少量平台线程。虚拟线程和go中的协程类似。虚拟线程和平台线程的作用不同，虚拟线程适合处理io密集型等待居多的任务，切换和调度都比平台线程块，但是在cpu密集型上面因为都是占用cpu资源，所以不如直接创建平台线程。

两种实现：虚拟线程和平台线程

  • 平台线程：Java中的默认线程实现，1:1封装os内核线程；线程调度由os内核态完成，切换时开销较大；创建线程时默认VM栈1MB，自带Program Counter（PC），不能无限创建。
  • 虚拟线程：JDK21之后的线程实现，M:N封装平台线程，M»N；线程调度由用户态JVM的ForkJoinPool完成，切换开销小，创建线程栈的资源开销小可以动态伸缩，单个JVM进程可以创建上百万个虚拟线程。在IO密集型需要等待任务上有优势，反之在cpu密集型上不如直接创建平台线程。
Q：如何实现线程安全、数据一致、原子操作？
A：

保证原子性：AtomicInteger、Sychronized上锁；保证可见性：Synchronized，Volatile；保证有序性：禁止指令重排一类。

具体来说实现线程安全，就是保证编写多线程代码同步和通信时的 原子性、可见性、有序性。

实现方法也很常见：

  • 乐观锁：CAS、Version版本号先修改在比较不同则回滚。
  • 悲观锁：Synchronized、ReenterantLock等等
  • Volatile保障使用乐观锁时的可见性，搭配乐观锁CAS使用。

参考((20260824102745-stkak49 ‘基本使用流程’))，大概是几种方法，核心就是接收了runnable（无返回值）和callable（有返回值）的线程通过thread.start()执行，如果是线程池executor就是submit执行，callable可以通过future接收返回值等。也可以通过((20260822150735-u3o37s4 “CompletableFuture”))接收callable+线程池的方式来编排组织线程同步和执行顺序。
Q：如何中断线程？interrupt是如何让线程抛出IterruptedException异常的？
A：

首先需要说明interrupt仅仅只是给线程设置一个中断状态，是否响应需要依赖runnable内部的阻塞状态。是否响应中断需要依赖两种，一种是自动响应中断的Thread.sleep, Thread.join以及object.wait和future.get等io方法，如果是cpu循环执行的话，那么这种就需要手动在循环中判断interrupt状态并return或者抛出异常了。这个解释同时说明了上述两个问题。

关于如何中断线程，其实不同的主体有不同的方法，核心还是使用interrupt：

  • thread的interrupt方法

  • ThreadPoolExecutor提交后可以使用返回值future的cancel方法，cacel(true)表示可以给正在运行的方法发送iterrupt方法，反之cancel(false)就不会给正在运行的线程发送。

  • ThreadPoolExecutor还有两个方法，一个是shutdown一个是shutdownNow

    • shutdownNow：拒绝所有任务提交，不处理任务队列中的所有任务，给当前所有正在运行的线程发送interrupt方法。
    • shutdown：拒绝所有任务提交，但是任务队列和正在运行中的线程不会做任何干扰。

Q：线程有哪些状态？
A：
参考((20260430163856-v6l2y2d ‘线程有哪些状态’))，线程的状态有NEW初始化状态，刚刚创建完没有被start；Runnabel状态，同时包括ready和running状态，在running状态的可以通过yield让渡cpu给别的线程执行，在ready状态的等待cpu调度；waiting状态是在线程运行时因为object.wait join lock.park等被切换过去的状态，通过notify unpark，notifyAll可以切回runnable状态；timewating就是wating切换的实现状态，同时加上可以自动响应中断的Thread.sleep(指定时间)；blocked一般都是运行线程为了获取锁（lock，synchronzied）等等进入的，需要等待锁释放获取到锁才能切会runnable状态；线程执行完成后进入terminated状态，回收vm栈和program counter等系统资源。
Q：sleep、wait、blocked有什么区别？
A：

触发，释放锁不同。

sleep可以手动在线程的任何位置触发，不会释放任何锁，进入timedwaiting状态。时间到了后自动切入runablle的ready状态。

wait需要在获得lock后的同步块中触发，主动让渡锁出去，进入waiting状态，等待别人notify自己，得到notify后切入runnable的ready状态，cpu分配后重新开始竞争锁。

blocked是在竞争锁的过程中失败自动切入blocked状态，当有进程释放锁，会自动触发唤醒重新竞争。

并发锁

Q：了解哪些锁的种类，具体有哪些常用的锁？
A：

1、** 锁的种类：公平非公平，乐观悲观，排他互斥锁。

2、 常用锁

  • syncrhonized锁，内置对象锁，Object中实现，可以对任何非null对象使用synchronized上锁。
  • ReentrantLock锁，可重入锁，显式锁，默认非公平锁。可以设置为公平锁，自定义程度非常高。
  • ReadWriteLock锁，读写锁，适合读多写少的场景。读读共享，读写、写写互斥。
  • 自旋锁：等待锁的是不会阻塞，而是不断循环检查是否可以获取锁。优点是省的内核切换带来的开销，缺点是如果长时间自旋会一直占用空耗cpu资源。
Q：Synchronized内置对象锁是什么？加锁释放的逻辑？
A：
Synchronized锁借助JVM的Monitor对象自动维护，在存在竞争/竞争加剧的时候视情况进行锁升级。进入synchronized块/方法之前需要竞争指定对象的锁，退出时释放锁，竞争失败则阻塞进入blocked状态等待锁释放重新竞争。
Q：Synchronized锁的原子性、可见性、有序性？
A：

原子性不用多说，同步块对应的原子性；可见性，monitorenter，进入同步块之前先将主存中需要访问的共享变量复制到本地线程方法栈（VM栈）中，monitorexit，退出同步块之前将本地VM栈中的变量同步到主存中；有序性：synchronized不能确保指令不重排。

一个经典的例子就是DCL单例锁必须要给instance加volatile，不然多线程进行单例获取时，线程B可能会获取到先引用赋值后对象构造的非null instance对象。使用volatile，可以通过插入内存屏障来进行对象构造和引用赋值这两个指令重排导致单例获取的问题。

Q：Synchronized的锁升级流程？
A：

无锁，偏向锁，轻量锁，重量锁。

无锁：默认状态就是((20260501094731-8n8d3go “对象头监视器Monitor中的无锁状态”))，没有线程进行获取。

偏向锁：当有一个线程获取锁的时候，锁升级为偏向锁，记录当前线程和重入次数1。当这个线程再次获取时，因为是偏向锁，所以可以直接获取，同时重入次数+1。当有另外一个线程B获取的时候：加入当前线程A持有，那么锁升级为轻量锁，线程A重新持有轻量锁，线程B自旋CAS等待线程A释放锁。如果锁没有其他线程占有，修改偏向锁的偏向线程为线程B和重入次数为1。

轻量锁：多个线程并发请求锁、线程B请求线程A占有的偏向锁的时候，触发偏向锁向轻量锁的升级。源线程A继续持有轻量锁，线程B通过CAS自旋等待线程A释放锁。一旦CAS次数过多，轻量锁升级为重量锁。

重量锁：CAS次数过多，1、锁竞争激烈。2、单个线程持有锁时间较长，等待锁释放的线程CAS自旋次数过多占用过高CPU资源。此时替换轻量锁为由os内核的互斥变量mutex，减少cpu占用，避免无意义开销。

Q：什么是volatile，如何保证可见性和有序性？有什么代价？
A：

volatile，可见性通过读是必须从主存读，写时必须同步写入主存实现；有序性，在读/写volatile变量的操作前后加内存屏障，禁止前后的指令重排。什么代价呢？比读写普通变量更慢，具体表现是在1亿次i++的状态下，耗时大概在40倍左右（volatile变量耗时192ms，普通变量耗时5ms，40倍左右的开销）。

Q：什么是ReentrantLock？实现机制？和synchronized什么区别？三性怎么实现的？
A：

ReentrantLock是一种显式锁。

实现机制：CAS自旋+AQS队列同步器，同时维护volatile thread和volatile state变量。

和synchronzied什么区别：

  1. 一个是内置对象头监视器模式的锁，一个是显式锁。
  2. reentrantLock支持公平锁，多路condtion singla/await，显式加锁释放锁，可重入。

三性怎么实现的：

  • 什么是三性：可见性，有序性，可重入性。
  • 可见性：通过volatile实现。
  • 有序性：volatile变量禁止指令对ReentrantLock中的指令重排，同步块中也不会重排，结合happens-before实现禁止指令重排。
  • 可重入性：CAS+AQS+Volatile thread，state；当发现当前持锁线程为请求线程的时候，直接放行同时state+1；不是的时候，加入AQS队列；释放锁的时候state必定为1, 然后被扣为0接着释放。

Q：什么是CAS？CAS有哪些问题？什么是AQS？AQS是公平的吗？AQS有非独占模式吗？CAS和AQS是什么关系
A：

CAS就是comapre and set，先获取想要修改的变量，然后原子性（CPU总线锁定）的comapreAndSet，如果comapre expected和当前最新值相同，那么可以修改，反之继续在while循环中自旋CAS等待获取成功。CAS的问题源自于获取值 到 原子性的compareAndSet 和 获取想要修改的变量之间，存在ABA问题、获取失败时的自旋开销问题以及一次只能comapreAndSet一个变量的问题，多个变量需要封装为一个对象再做cas。

什么是AQS：抽象队列同步器 Abstract Queue Synchronizer，其实就是volatile state变量和CLH线程队列。CAS失败的线程如果都持续自旋带来许多不必要的CPU开销，通过组织AQS的CLH队列，让CAS失败的线程加入CLH队列，head就是当前持有锁的线程，head.next在head释放锁的时候unpark head.next，来cas获取锁。后面的线程进入队列后，如果前面不空，自己将自己park，等待前面的通知自己unpark。

AQS是公平的吗？并非，默认的ReentrantLock就是非公平的，竞争的线程在进入队列前没有自park的时候，可以cas，如果成功了就占用锁移动到队头节点。这就不是公平的。当然也可以设置ReentrantLock为公平的，此时只有进入AQS队列的可以acquire。

AQS有非独占模式吗？有的，tryAcquireShared和tryReleaseShared，可以在共享模式下释放和获取锁，一个unpark后面的链式unpark，大家一起共享一个锁。

CAS和AQS是什么关系？为了不让高并发场景CAS自旋的不必要开销，使用AQS CLH队列来维护等待线程队列。默认的像Atomic类的CAS就是一个do while循环。

ThreadLocal

Q：什么是ThreadLocal？什么原理？有什么限制？
A：

ThreadLocal是每个线程私有的变量，在子线程中获取父线程中的变量时为空，可以设置子线程自己的ThreadLocal。存储在每个线程的ThreadLocalMap< Key:WeakReference, Value: value>中，ThreadLocal是弱引用，存储的值是value。当ThreadLocal没有了外部的强引用的时候，一次System.GC()配合Thread.sleep(500)就可以清理掉这个ThreadLocal，但是此时value还存在ThreadLocalMap中，形成了内存泄露。

限制：子线程中无法访问（两种创建方式new Thread(()->{})和threadExecutorPool.submit(()->{})的子线程）父线程的threadLocal。

Q：可以在子线程中访问父线程的ThreadLocal的工具？
A：

一个是自带的InheritableThreadLocal，可以在new Thread中使用，但是不能使用线程池；另外一个是阿里的TransmittableThreadLocal和TtlExecutor，支持new Thread捕获父线程的ThreadLocal值。

具体来说：

  1. InheritableThreadLocal的问题是，只能在线程创建的时候捕获当前父线程的ThreadLocal/InheritableThreadLocal值，后续如果更新了itl的值，那么重新复用的线程输出的itl的值还是创建时的值，有延迟问题。
  2. TransmittableThreadLocal，阿里的父子线程传递Ttl，可以在new Thread中使用，也可以通过TtlExecutor创建线程池来捕获。每次线程start的时候都将父线程的Ttl复制到本地，子线程结束时自动清理避免ThreadLocal的内存泄露污染。

TransmittableThreadLocal和InheritableThreadLocal的区别就是一个是在任务提交/执行时进行Ttl的捕获，一个是在线程创建时做itl的捕获，这样就延伸出了线程复用时的使用差别。

Q：InheritableThreadLocal和TransmittableThreadLocal是否解决了weakReference带来的value内存泄露问题吗？
A：

并没有，虽然会自动清理，但是如果是一个singleExecutor的话，那么上一次线程使用的时候设置的threadLocal下一次线程使用的时候还会继续访问到。正确的做法还是使用完remove。

线程池

通过new ThreadPoolExecutor创建的线程池。

Q：主要参数
A：
主要参数有：核心线程数corePoolSize，最大线程数maxPoolSize，非核心线程存活时间keepAliveTime和TimeUnit，BlockingQueue WorkQueue，以及ThreadFactory线程工程和workQueue满的时候的拒绝策略handlerAbortPolicy。
Q：工作流程
A：

工作流程是：假定一个ThreadPoolExecutor，corePoolSize=2, maxPoolSize=4, keepAliveTime=60s，使用ArrayBlockingQueue(2), AbortPolicy使用抛出异常并丢弃。

  1. 第一个任务被submit或者execute，创建核心线程c1并执行
  2. 第二个任务提交，创建核心线程c2并执行
  3. 第三个任务提交，此时corePoolSize满，workQueue没有满，加入任务队列。
  4. 第四个任务提交，此时corePoolSize满，workQueue没有满，加入任务队列。
  5. 第五个任务提交，此时corePoolsize和workQueue都满了，此时创建非核心线程e1，优先执行第五个任务。
  6. 第六个任务提交，此时corePoolsize和workQueue都满了，此时创建非核心线程e1，优先执行第六个任务。
  7. 第七个任务提交，此时corePoolSize和workQueue都满了，同时maxpoolSize也满，根据拒绝策略handler进行处理。
Q：一个线程池最多同时处理多少任务
A：

对于并发同时处理多少任务：具体的，同时可以接收maxPoolSize + len(workQueue)个任务。如果其他线程处理的快的话，不止接收这么多。

注：一般来说是这样，但是如果workQueue是无界队列，那么最大同时处理上限就是corePoolSize个。

Q：对于任务队列
A：
分为有界队列和无界队列两种，有界队列就是ArrayBlockingQueue，无界队列有LinkedBlockingQueue，DelayedBlockingQueue等，SynchronousQueue是特殊的任务队列，类似于Go中的Chnnel(0)，必须要线程池中有空闲线程时才能接收提交，否则执行拒绝策略。
Q：对于拒绝策略：分为四种，
A：
  1. AbortPolicy，抛出异常并丢弃，这个异常需要在提交者所在线程中显示处理。
  2. DiscardPolicy，静默丢弃，不抛出异常。
  3. CallerRunPolicy，提交者所在线程执行提交的任务。
  4. DiscardOldestPolicy，丢弃workQueue中的第一个，然后重新提交。
Q：关于submit和execute的区别：
A：

execute执行的异常需要在runnable内部显式处理，如果没有处理直接抛出那么当前的worker线程会死亡，等待线程池新建下一个。execute抛到上面的异常可以有ThreadFactory通过thread.setUncaughtExceptionHandler 和 ThreadPoolExecutor的匿名内部类中实现的afterExecute方法拿到，但是无法处理只能记录。

submit提交后，runnable执行过程中产生的异常被封装在Future中，在get的时候外面包上try catch进行处理。

Q：对于execute抛到上面的异常，两种记录方法：
A：

对于线程工厂，可以在创建线程时给thread设置UncaughtExceptionHandler来记录execute执行过程中抛出的异常。

对于线程池，可以使用匿名内部类实现afterExecute方法，记录execute抛出的异常，处理submit抛出的异常。

Q：线程池的关闭方式shutdown和shutdownnow区别？
A：
shutdown是等待线程池处理完所有任务后再关闭，shutdownnow是拒绝所有任务提交，不处理workQueue中的所有任务，给所有正在执行任务的线程发送interrupt信号，等待中断。
Q：线程池创建需要注意什么？
A：

无界队列和corePoolSize搭配的时候，不会创建非核心线程。

核心线程数量，队列类型，拒绝策略。

Q：预定义的四种线程池是什么？
A：

newFixed，newCached，newSingle和newScheduled

具体的，基本上都是使用无界队列。

newFixed的corePoolSize = maxPoolSize，使用LinkedBlockingQueue，使用固定数量的核心线程来处理任务。

newCached的corePoolSize = 0, maxPoolSize= Integer.MAX，使用SynchronousQueue来不断创建新核心线程处理任务。

newSingle就是corePoolSize = maxPoolSize =1, 使用LinkedBlockingQueue，保证串行执行任务。

newScheduled就是使用无界队列DelayedWrokQueue来延时执行任务，并发定时任务上限就是corePoolSize。
