按照学习顺序来组织一下网络的一些八股，同时也方便以后复习的时候线性阅读，减少跳跃式阅读。

Q：OSI七层、TCP/IP五层？
A：

OSI七层：应用、表示、会话、传输、网络、数据链路、物理。

TCP/IP五层：应用、传输、网络、数据链路、物理。

具体的：

  • 应用层：应用报文协议在这上面工作，常见的协议有http、https、dns、ftp、smtp、esmtp、dhcp

    • http：bs数据传输。
    • dns：通过域名解析ip地址，报文长度大于512B改用tcp，小于使用udp
    • ftp：常见的文件传输，基于tcp
    • smtp：邮件传输协议，无加密，基于tcp。esmtp实现加密和权限校验。
    • dhcp：动态分配ip地址，基于tcp。

  • 表示：进行数据处理，常见的就是编解码、加解密、解压缩。例如：TLS加解密、rtsp转流、flv编解码，gzip解压缩。

  • 会话：管理应用间会话。session、cookie工作在这个上面。

  • 传输：tcp/udp传输，进程之间的通信，传输携带port的segment。

    • 实现差错控制、流量控制、可靠传输，单位是segment。

  • 网络：ip packet的传输，携带destIp和srcIp。负责将数据从srcIp传输到destIp。

    • 实现路由选择、分组转发、拥塞控制、差错控制、流量控制、可靠传输，单位是含src/destIp的packet。

  • 数据链路： mac frame传输，携带destMac和srcMac。负责相邻节点之间bit流的可靠传输，纠错以及流量控制。

  • 物理：相邻节点之间传输透明bit流。

Q：网络分层的原因
A：

分层减少每层差错，单独控制和完善。

  • 各层相互独立
  • 整体灵活
  • 每层的问题单独解决
Q：从输入 URL 到页面展示到底发生了什么？
A：

首先进行URL解析，然后DNS域名解析url对应ip，然后需要进行tcp三次握手在服务端和浏览器之间建立连接，连接建立成功后，封装应用层报文进行请求，响应获取后浏览器解析html并触发绘制。

ARP目标mac查询以及路由器和交换机转发：以tcp报文为例，源ip和目标ip分别是当前客户端A和目标B服务器ip，源mac地址是a-mac，目标mac地址通过ARP广播获取：（1）如果服务器B在本地局域网则返回携带本机mac的ARP Reply。（2）如果不在，通常封装目标mac为本地路由器的r1-l-mac。封装完成后frame由交换机按mac地址进行转发。路由器收到后解frame，根据目标ip查询，如果在本机则ARP 目标ip的mac进行封装转发，如果不在本机则在路由表中查询得到下一跳ip，同样通过arp得到下一跳ip的mac地址后封装转发（r1-r-mac，r2-l-mac）。r2收到后进行类似操作，目标ip对应的目标服务器在本地，通过arp广播得到b-mac，最后封装frame发送至目标服务器。

当用户在浏览器中输入 URL 并按下回车后，浏览器首先会解析 URL，获取协议、域名、端口和请求路径等信息，然后进行 DNS 域名解析。首先检查浏览器缓存、操作系统缓存和 Hosts 文件，如果没有命中，则向本地 DNS 服务器发起递归查询。本地 DNS 服务器如果也没有缓存，就依次向根域名服务器、顶级域名服务器和权威域名服务器进行迭代查询，最终获得目标服务器的 IP 地址并返回给客户端。获取 IP 后，浏览器需要与服务器建立连接，如果使用 TCP，则通过三次握手建立 TCP 连接；如果是 HTTPS，还需要进行 TLS 握手，验证服务器证书并协商加密密钥。随后浏览器构造 HTTP 请求报文，经过 TLS 加密（HTTPS）后交给传输层，TCP 根据实际发送情况将数据组织成报文段，并添加源端口、目的端口、序列号等 TCP 首部信息；接着交给网络层，IP 协议添加源 IP、目的 IP 等信息，形成 IP 数据报，并根据路由表确定下一跳；然后交给数据链路层，如果使用 IPv4 以太网，则通过 ARP 获取下一跳设备的 MAC 地址，将 IP 数据报封装成以太网帧，添加源 MAC、目的 MAC 和帧尾校验信息，最后通过物理网卡发送。数据在网络中传输时，交换机根据目的 MAC 地址转发以太网帧，路由器根据目的 IP 地址查询路由表并转发 IP 数据报，每经过一次路由器的三层转发，通常都需要重新封装链路层帧，因此 MAC 地址逐跳变化，而源 IP 和目的 IP 在不考虑 NAT 的情况下通常保持不变。数据到达服务器后，服务器从数据链路层到应用层逐层解封装，TCP 完成数据重组并交付给应用程序，Web 服务器解析 HTTP 请求、执行业务逻辑并生成 HTTP 响应，再经过相应的协议封装返回给客户端。浏览器收到响应后，解析 HTML 构建 DOM 树，解析 CSS 构建 CSSOM 树，结合两者生成渲染树，随后进行布局（Layout）、绘制（Paint）和合成（Composite），最终将网页显示在屏幕上。在解析页面的过程中，如果遇到 CSS、JavaScript、图片等资源，浏览器还会根据需要发起额外的网络请求。需要注意，现代浏览器可能复用已有连接，而 HTTP/3 基于 QUIC，不需要 TCP 三次握手。

Q：ARP目标mac查询以及路由器和交换机转发
A：
以tcp报文为例，源ip和目标ip分别是当前客户端A和目标B服务器ip，源mac地址是a-mac，目标mac地址通过ARP广播获取：（1）如果服务器B在本地局域网则返回携带本机mac的ARP Reply。（2）如果不在，通常封装目标mac为本地路由器的r1-l-mac。封装完成后frame由交换机按mac地址进行转发。路由器收到后解frame，根据目标ip查询，如果在本机则ARP 目标ip的mac进行封装转发，如果不在本机则在路由表中查询得到下一跳ip，同样通过arp得到下一跳ip的mac地址后封装转发（r1-r-mac，r2-l-mac）。r2收到后进行类似操作，目标ip对应的目标服务器在本地，通过arp广播得到b-mac，最后封装frame发送至目标服务器。
Q：DNS查询
A：

分两种，DNS递归查询和DNS迭代查询。

通常我们浏览器输入URL后，就是client DNS递归查询 给本地DNS Server，然后本地DNS Server进行DNS迭代查询：先查本地缓存有没有，没有则询问根DNSServer；根DNSServer返回管理指定顶级域名DNS Server的委派；本地DNS Server再询问顶级域名DNS Server，顶级域名DNS Server再返回权威域名服务器地址；本地DNS Server询问权威域名服务器，权威域名服务器查询域名对应的资源比如A记录（域名-ipv4）、CNAME（域名-域名）记录返回给本地DNSServer，本地DNS Server得到对应ip后返回给client。（如果返回的是CNAME，那么本地DNS Server可能需要再进行一次迭代查询，查询CNAME中对应ip的地址。CNAME会增加潜在的DNS迭代域名解析次数，但是有缓存就不需要）。

Http

Q：Http是什么？
A：
Hyper text transfer protocol，超文本传输协议。
Q：Http响应码？
A：
200请求成功；302临时重定向，但是访问的资源还在，需要使用别的url访问；304资源为修改，告知客户端可以继续使用缓存；400客户端请求错误；404请求url不存在；401鉴权失败，403权限补足；500服务器内部错误；502 网关错误 bad gateway。
Q：Get和post的区别？
A：

用途、body、缓存。

1、用途不同：get用于请求资源，服务端要保证多次get的幂等性。post用于写请求，天然不幂等。

2、是否携带request body：默认get不携带body，参数在路径中添加（pathvariable或者requestprarm）；post使用body传递参数。

3、是否可被缓存：get请求的结果可以被缓存；post请求的结果无法缓存。通过http报文中的method字段进行区分。

Q：Http和Https有什么区别？
A：

是否加密、握手次数、默认端口。

1、是否加密：https在http和tcp之间的表示层使用ssl/tls进行加解密。

2、握手次数：https连接建立还有一次ssl/tls握手。

3、默认端口：http默认80端口，https默认443端口。

Q：URI和URL是什么？encodeURIComponent和encodeURI什么区别？
A：
URI是统一资源标识，URL是统一资源位置，更侧向资源的访问。一个URL同时也是URI，可以说URL是URI的子集。encodeURIComponent和encodeURI都是对URL进行再编码，区别是encodeURIComponent会对uri中的特殊字符比如&=进行再编码。实践中只有encodeURIComponent有用，因为只需要编码部分字符串比如keyword={xxx}, xxx=java&mysql，使用encodeURIComponent对&进行编码。
Q：Http1.0和Http1.1的区别？管线化的问题
A：

长连接、缓存控制、管线化请求（pipelining requests）

长连接：多个http请求维持使用同一个tcp连接，参数connection: keep-alive，http1.1的默认参数，不需要显式添加。

管线化：解决http1.0的请求队头阻塞（请求B必须等待请求A的响应A回来后才能发送），可以在响应没有回来的时候发送多个请求。

管线化的问题：但是在服务端的响应写出需要按请求顺序写出，这是请求响应模型的响应队头阻塞。同时http1.1的管线化请求并没有被浏览器大规模的支持，所有更常见的情况还是为了提升请求的并发度，会建立多个tcp连接来进行请求，而不是在一个tcp连接上管线化请求。

Q：Http2什么改进，什么缺陷？
A：

二进制帧格式、首部压缩、stream消息解决请求响应模型的队头阻塞；问题就是TCP有序接收导致的队头阻塞。

Http2重新定义二进制帧格式，支持首部压缩，公共部分使用索引号表示。

支持stream化每一个请求（比如HTML请求、CSS请求、JS请求），一个tcp连接的请求中可以携带多个stream-id的frame，每个frame中包含指定的stream-id。接收端根据frame中的stream-id中的内容进行http2消息组装。解决了之前「一个tcp连接中请求的队头阻塞和响应的队头阻塞」。响应时只要指定stream-id的数据完整且已经能组装为一个http消息就可以处理并返回。

server-push：服务端可以主动推送，不过收益有限，支持的浏览器也不多。

存在的问题：TCP传输层队头阻塞。因为TCP传输是可靠有序的，所以当TCP#1, TCP#2, TCP#3, TCP#4, TCP#5中的TCP#3丢失了，此时接收端无法绕过TCP#3将TCP#4~5交付给Http2，这样导致多个stream受到影响。TCP按序读取，所以会有队头阻塞问题，即使后面的TCP段到达且4~5段中有完整的一个stream消息，但只要中间有一个丢失了，应用层也无法直接读取后面的。

Q：Http3什么改进？
A：

Http3基于udp的quic：quic建立连接只要一个RTT，基于udp无tcp的队头阻塞问题，连接复用。

  • 无队头阻塞：http3支持不同stream的独立交付，stream5-framex的丢失不会导致后来的stream7的无法交付。
  • 连接建立1RTT
  • 连接复用：原来的连接基于ip port的四元组确定，现在使用统一连接id标识，网络连接变化（比如从wifi切流量）但是上下文信息不变（连接id、tls秘钥），则继续复用原TCP连接。
Q：什么是缓存控制？
A：

缓存控制，也叫cache control，是强制缓存的一种。

强制缓存：客户端请求后，服务端响应结果携带cache-control和expire，指定这个响应过期的相对时间和绝对时间。客户端将响应缓存在本地，下次请求时如果没有过期，则复用本地缓存中的响应；如果过期了，进行协商缓存。

协商缓存：强制缓存过期时使用协商缓存，client发送请求 携带本地缓存中的etag，server端和本地资源校验，如果etag相同则返回304 继续复用之前的响应，如果etag不相同 server端则200返回新的响应。

Https

Q：为什么需要使用Https？有哪些不使用https导致问题的例子。
A：

Https使用ssl/tls加解密。最出名的一个https中间人劫持例子是2018 年的MyEtherWallet 劫持。

简单讲讲这个MyEtherWallet 劫持例子：攻击者通过劫持BGP将一部分用户的流量导向自己的DNS服务，这些流量请求后续进入攻击者伪造网站，攻击者伪造网站仿造证书过期让用户点击信任证书，如果用户接受攻击者证书，攻击者就可以建立两条 TLS 连接，分别与浏览器和真实服务器通信，从而读取和篡改经过自己的明文数据。

本质上和https无关，这个问题的根因在与用户信任了攻击者证书。

Q：Https的基本加密原理？
A：
简单来说，我们要给网站上https需要先向权威机构申请根证书机构CA申请证书，得到公钥私钥，私钥放在服务器上，公钥传递给所有客户端。客户端信任后，下次发送请求的时候用公钥加密并发送信息给server，中间链路上即使有中间人攻击，中间人没有私钥自然也无法读取和篡改，到server的时候因为是非对称加密（对称加密是指用同一把钥匙上锁和开锁，非对称加密指的是A钥匙加密、B钥匙解密）。
Q：Https连接的建立流程？什么是tls四次握手？
A：

Https先tcp三次握手，然后tls四次握手，最后建立连接使用会话秘钥进行加密连接。

tls四次握手：tls四次握手，两个RTT来回是tls1.2的规范，实际上tls1.3只需要一个RTT即可完成。

  • 1、ClientHello，客户端发送：生成的client random随机数，支持的加密算法。
  • 2、ServerHello，服务端接收后发送：生成的server random随机数，确认的加密算法（后续用于加密client&server random 以及 pre-master-key），以及公钥证书。
  • 3、客户端接收公钥证书后首先校验证书，没问题则生成随机数pre-master-key，并使用确认的加密算法生成后续加密解密需要的「会话秘钥」，随机数会使用公钥证书加密传输到server端。
  • 4、server端收到并使用私钥解密pre-master-key，生成「会话秘钥」。

后续的数据传输都使用「会话秘钥」进行加密。

Q：为什么tls需要生成会话秘钥而不是直接使用公钥？
A：

先说明一点，tls加密的过程是通过非对称加密协商出对称加密秘钥，之后使用对称加密秘钥进行数据传输。这里的对称加密秘钥就是生成的会话秘钥。

为什么需要对称加密？

  • 非对称加密开销大。
  • 非对称加密能够加密的明文长度受非对称加密秘钥长度的限制。
  • 如果攻击者录制了tls流量，之后获取到了服务器私钥也无法解读出之前流量的明文。
Q：为什么说公司一定能直到你在访问哪些网站？甚至查看了哪些https内容
A：

通过中间人注入，你是用的电脑就是公司的，安全部门不仅仅只是抓流量这么简单，通过安全软件安装的一系列中间证书，你的流量在公司的网关处可以被解密为明文，然后公司的网关再放行给你访问的网站，你访问的网站的响应他们也可以抓到明文。

如果员工使用的是公司管理的电脑和网络，公司可以通过 DNS 日志、目标 IP、TLS SNI、代理日志以及终端安全软件等方式了解网站访问情况，并不一定需要解密 HTTPS。

对于 HTTPS 内容，公司还可以通过安装受信任的企业根 CA 证书，结合 TLS 检查代理实现中间人解密。具体来说，企业网关分别与员工电脑和目标服务器建立独立的 TLS 连接，使用企业 CA 签发的替代证书取得客户端信任，从而在网关处解密、检查并重新加密 HTTP 请求与响应。因此，HTTPS 能够防止未被信任的中间设备窃听和篡改，但不能保证通信内容对用户主动信任的企业代理保密。

Q：什么是tls1.3？
A：

tls1.3，server和client各自生成临时秘钥（公钥和私钥），通过1RTT交换公钥，通过「客户端秘钥+server公钥」和「client公钥+server私钥」生成「共享秘钥」，完成连接建立。

很神奇吧，椭圆加密算法。

Q：为什么TLS1.2+Http2需要2RTT才能建立，而Http3+TLS1.2只要1RTT？
A：

下面两张图就能概括为什么了。简单介绍下：TLS1.2+Http2需要先建立tcp连接，在tcp握手的最后一个client ack时可以顺带发送clienthello，后面的tls握手时，在客户端通过非对称秘钥协商得到会话私钥为止，大约2RTT。TLS1.3+Http3需要1RTT，初始的QUIC initial就带上clienthello，即使使用tls1.2，在第三次客户端请求时就已经协商好会话秘钥了，客户端就可以直接发送加密的http请求了。如果使用tls1.3，1RTT建立完成，客户端服务端互相发送公钥，客户端想要发送加密请求也得等到第三次了。

TCP

Q：TCP是什么？
A：

面向一对一连接、可靠有序的，基于字节流的传输层通信协议。

  • 面向一对一连接的：通信前需要先建立连接，一对一，进程之间的通信。
  • 可靠有序的：可靠的字节流传输，如果乱序或者有字节没有顺序接受到，需要等待重试或者丢弃。
  • 基于字节流的：TCP传输的数据是一连串无结构的字节流。
Q：有一个ip的server监听一个端口，最多可以建立多少tcp连接？
A：
客户端ip数量 * 客户端可用端口数量 = 2^32(2^(8*4)) * 2^16(65536) = 2^48 个，但实际能建立多少个还需要收到服务端内存限制以及可创建文件描述符数量限制。
Q：TCP三次握手，TCP请求响应中的seq和ack。
A：

先说seq和ack，然后再说tcp三次握手。

seq：当前tcp报文中第一个字节的序列号，如果是tcp握手阶段可以是client或者server的initialized serialized number初始化序列号。

ack：期望对方发送的第一个字节的序列号，ack number-1就是已经接收到的。

TCP三次握手：

  • 客户端和服务端开始都是closed，之后server进入listen监听，client发送syn请求，携带client isn初始序列号：seq=client_isn，ack为空。发送完成后client进入syn-sent状态。
  • server端接收到client_isn后，返回syn+ack报文：seq=server_isn，ack=client_isn+1，发送完成后server进入syn-rcvd状态。
  • client接收到syn+ack后，返回ack报文：seq=client_isn+1, ack=server_isn+1。client进入established状态。在第三次握手的时候，可以携带数据进行传输。
  • server端接受到ack后，进入established状态。

最后给一个client和server的seq和ack表格：

seq ack
client TCP三次握手 syn 1000=client_isn null
server TCP三次握手 syn+ack 5000=server_isn 1001(client_isn+1)
client TCP三次握手 ack 1001 5001
client 普通请求 携带字节Hello 1001 5001
server 响应 5001（纯ack的seq可以不变化，设置为5001） 1006
client 请求 携带aoi 1006 5001（没有收到数据，所以ack还是5001）
server响应 5001（没有发送数据，5001） 1009（1006、1007、1008，期望收到的下一个就是1009）
Q：TCP三次握手，为什么不能是两次握手？
A：

三个理由：避免重复连接、减少资源开销、同步序列号保证后续的可靠字节流传输

避免重复连接：TCP两次握手时，Server端在发出syn+ack后分配资源建立连接，也无法确定是否是client历史丢失的syn报文。如果使用三次握手，在第三次握手的时候client判断延迟的syn+ack报文同时返回RST reset报文（本质上就是让client判断历史连接并避免建立重复连接），不让server端建立连接。

减少资源开销：如果两次握手，syn多次丢失时，client会进行多次重传导致server端建立多个无效历史连接。

同步序列号保证后续可靠字节流传输：同步client_isn和server_isn，在后续连接建立后通过seq和ack的交替保证字节流的可靠有序传输。

Q：TCP三次握手时的重传逻辑？
A：

syn报文丢失，client重传。syn+ack丢失时，client和server都会认为是自己发送的报文超时，client传syn的同时server传syn+ack。第三次的ack报文丢失时，server发现客户端响应一直每到，重传syn+ack。

注：ack报文丢失不会重传，syn报文丢失重传。

Q：TCP连接为什么需要随机初始序列号？
A：

避免接收历史报文；增加黑客伪造四元组tcp报文的难度。

避免接收历史报文：TCP连接使用四元组+seq num来标识，如果都使用相同的seq num初始化，那么历史连接中晚到的报文就会被当前连接读取。

增加黑客伪造四元组tcp报文的难度：使用随机序列号，增加黑客的伪造难度，提高tcp的安全型。

Q：什么是半连接队列？什么是SYN攻击？如何避免SYN攻击？
A：

Server端进入listen状态后维护一个半连接队列和全连接队列，在收到syn报文返回syn+ack后，将这个连接加入半连接队列，若一直没有响应则重传syn+ack。syn攻击就是通过伪造ip向指定服务器发送大量syn包但不返回ack，使半连接队列队满，无法处理新的syn请求。

如何避免syn攻击：

  • 减少syn+ack重传次数
  • 提高半连接队列容量
  • syncookie，synproxy，避免直接建立半连接添加到半连接队列，过滤伪造的syn攻击，只有确认能返回ack的才允许后续加入半连接队列。
Q：在ip层分片，为什么在tcp层还需要mss呢？
A：

其他几个概念：什么是mtu和mss？什么是最大ip数据报文，什么是传输时ip数据报文分片？ip层传输和tcp传输的不同？

mtu和mss：mtu是max tranfer unit 最大传输单元，也就是最大ip数据报文的大小 1500B，不算扩增字段，如果ip首部和tcp首部都是20B，那么最大tcp数据报文长度是1460B（即mss=1460B，mss是max segment size）。

最大ip数据报文和ip层传输时分片：ip数据报文的长度本身不做限制，如果传递大小4000B，那么在传输时会分片为三个ip分片（每个最大MTU）。ip层在传输时如果一个ip分片丢失，那么这个ip数据报文就不能交付，需要所有分片一起重传。这也是ip和tcp的不同，tcp层一个报文丢失，只会超时重传这一个。

最后回答为什么tcp层为什么需要mss：避免 IP 分片，降低丢包后的重传代价。

  • 通过主动限制tcp层报文长度，避免ip层分片，提高网络传输效率。主动在tcp层进行分片，避免ip层丢失一个分片导致的所有分片超时重传（具体说，ip层进行的分片，某个分片丢失会导致ip数据报文无法交付，这样client端无法收到tcp的确认，ip层无法重传，但tcp层又不清楚ip层分片了，此时超时后只能整个重传tcp）。

注：一个4000B的tcp报文，在发送的时候可能是一个tcp连接中多次mss=1460B的数据传输，通过seq保证有序提交和可靠传输。

Q：TCP的四次挥手？
A：

TCP四次挥手过程中定义主动断开方为A，被动端口方为B。A的状态有established、fin wait1、fin wait2以及time wait，B的状态有established、close wait以及last ack。最后的状态都是close。报文传递是两个RTT的fin和ack。

具体的：

  • A发送FIN报文，进入FIN WAIT1，此时不再发送数据，还可以接收B的响应。
  • B收到FIN报文，进入CLOSE WAIT阶段 处理和响应剩余数据，不再接收请求，同时发送ack让A进入FIN WAIT2阶段。
  • B处理完数据后，发送FIN报文，进入LAST ACK阶段，此时不再进行收发。
  • A收到FIN报文后，响应ACK报文给B，B在收到后进入ClOSE关闭，A进入TIME WAIT，在等待两个报文最大存活时间后（2msl=max segment live time）也关闭。
Q：为什么time wait要等待2msl？
A：

避免历史报文影响新tcp连接；确保当前tcp连接正确关闭。

避免历史报文影响新连接：设置2msl，确保所有之前的报文都活不过2msl。

确保当前tcp连接正确关闭：如果4ack丢失后，server端迟迟无法关闭直到1RTO（Retransmission Timeout 重传超时）时触发fin报文重传，此时client接收到fin报文后再传ack并重置2msl计时器。

如果client直接关闭，那么server没能关闭就会一直占用内存和端口资源。

设置2msl，确保ack报文丢失后，server端重传的fin报文能被client接收。

Q：为什么需要time wait阶段？
A：
避免历史报文影响新tcp连接；确保当前tcp连接正确关闭。
Q：time wait过多什么危害？为什么time wait过多？
A：
占用内存和端口资源。time wait过多的原因：http长连接没开，开了长连接但是请求太多了。
Q：如果已经建立了连接，客户端突然终止没机会四次挥手以及进程突然终止？
A：
如果四次挥手了，tcp连接和两边资源都关闭了。如果没有四次挥手，B端有保活计时器，隔一段时间进行探测，如果一直没有响应则断开连接，如果有响应则重置保活计时器时间并保持连接。
Q：为什么需要四次挥手？可以三次挥手吗？
A：

TCP 四次挥手是因为全双工连接需要分别关闭两个发送方向（A端不发送数据传FIN报文，B端不再发送数据传fin报文）；如果被动关闭方能够同时发送 ACK 和 FIN，就可以变成三次挥手。

四次挥手分别是A端的fin ack和B端的fin ack，服务端需要处理数据并进行响应，整体流程是保证两边完成剩余工作、没有数据需要收发的情况下关闭tcp连接。

可以三次挥手替代四次挥手：如果B端没有数据要处理和发送，可以直接同时合并发送ACK和FIN报文，此时就是三次挥手。另外一种情况就是延迟ack到B端可以关闭数据发送并发送fin报文的时候，合并发送ack+fin报文。

Q：TCP重传机制有哪些？分别解决了什么问题？拿一个例子来说明？
A：

超时重传，快速重传，选择性重传SACK，重复重传DSACK。

超时重传：发送方发送数据时开启计时器，超过1RTO（略大于1RTT）时重传。

  • 问题：网络延迟时很多报文都需要等待超时重传，等待时间过长。

快速重传：发送方连续收到多个有相同ACK序列号的ACK报文，此时触发重传。

  • 问题：快速重传不知道是传一个还是传多个，如果是seq3~6都丢失了，也只能从seq3开始重传。

SACK：selective ack，接收端返回ack和sack区间，[ack, sack[0])就是丢失的部分，需要重传。

  • 问题：如果需要重传，不确定具体原因是ACK丢失/数据延迟型的重复接收，还是数据丢失的情况。

DSACK：duplicate selective ack，重复选择性重传，接收端如果收到重复数据，会使用DSACK描述并返回。发送端收到后可以判断前一次重传是否多余（ACK丢失、数据延迟，重传多余；重传有效：数据丢失）。

例子可参考：onenote/网络

Q：TCP的滑动窗口？为什么需要滑动窗口？什么是累积确认？窗口大小由哪方决定？接收窗口和发送窗口的大小相等吗？
A：

TCP Sender发送一个Data报文 Receiver返回一个ACK的方式比较慢，使用滑动窗口表示剩余可以发送的数据，已经发送的数据缓存在滑动窗口中，没有满的时候都可以持续发，当R返回ack后，可以将ack前面的数据从sender-window中移除。

什么是累积确认：举个例子加入seq500~599和seq600 ~ 699同时发送，第一个的ack600丢失，此时第二个的ack700可以直接覆盖前一个，对ack报文的丢失容错较高，减少重传。

窗口大小由哪方决定：主要有R端决定，S端的可发送窗口大小不能超过R的可接收窗口。R会在每次返回ack的时候携带剩余R-window-size，避免S端一次发送过多内容导致R无法处理。

接收窗口和发送窗口的大小相等吗：不一定，一般是R-window约等于S-window，因为R端返回ack同步R-window的时候有延迟，可能会出现R处理较慢但S-window又比较大的时候，也回出现R处理比较快但S-window比较小。总体大小相等，但受网络延迟和R端处理能力的影响，S-window和R-window会有波动。

Q：TCP的流量控制？什么是糊涂窗口？
A：

每次R返回R-window-size中的剩余大小来让Sender调解Sender-window-size，如果返回的wind=0,则sender不再发送而是开启定时任务询问receiver剩余wind大小，当wind>0时再重新发送。

糊涂窗口：当R太忙了，r-window-size会越来越小，sender收到后会条件window-size，即使是小窗口的报文也会发送，而R又来不及处理，导致两边最后windsize都到0。

Q：如何处理糊涂窗口？
A：

Receiver不发送小wind，Sender不发送小数据。

Receiver不发送小wind：如果wind<min(mss or 接收缓冲区大小的一半)（max segment size，ip层报文最大长度，包含ip首部20B和tcp首部的20B，1500B）时直接返回0，当wind>mss时再返回wind。

Sender不发送小数据：Nagle算法。

Q：什么是Nagle算法？什么是延迟确认？为什么Nagle算法不建议和延迟确认一起用？
A：

Nagle算法，当有已发送未ACK的数据时，新产生的小数据先缓冲直到ACK返回（ACK返回后，组合这些小数据一起发送） 或者 积累到较大的数据量时 在发送。本质上是延迟发送，可以减少Sender的小数据发送。

延迟确认：seq100~199 和 seq200~seq299前后到达时，先不返回前一个的ack，后一个处理完成后一起返回ack 300。本质上就是延迟确认。

不适合搭配一起使用，一个是延迟发，一个是延迟接收，两个一起搭配可能会造成更大的延迟和性能问题。

Q：TCP的拥塞控制？
A：

发送端在确定发送速率的时候，不仅要考虑接收端的接收能力，还要考虑是否会使网络发生拥塞。因此通过拥塞窗口cwnd和接收窗口rwnd来维护发送窗口swnd，调节接收能力。

前置概念：cwnd、rwnd、swnd，swnd = min(cwnd, rwnd)，其中cwnd是crowded window拥塞窗口。

拥塞控制：

  • 慢开始：从初始cwnd=1开始逐步增加cwnd, 然后每次传输轮次后不断倍增cwnd直到达到ssthresh=16。
  • 拥塞避免/加法增大：达到ssthresh后，每次传输轮次完成后cwnd+1mss。
  • 乘法减小ssthresh，重新慢开始：网络拥堵出现ACK超时时，乘法减小ssthresh为当前cwnd/2，然后重新进入慢开始。
Q：TCP拥塞控制的另一种：快重传与快恢复？
A：

当Receiver收到失序到达的报文立刻ack，Sender端收到多次相同的ack时触发快重传，同时进入快恢复算法（如果当前是在拥塞避免 加法增大环节时）：ssthresh设置为当前cwnd的一半，cwnd设置为ssthresh开始拥塞避免 加法增大。

使用快重传和快恢复的原因是：仍然有多次重复ack收到表示网络也没有那么拥塞，但前一次丢失可能有多种原因，所以进入快恢复阶段减少swnd，没必要一次直接将cwnd降到1。

Q：为什么有了流量控制，还要拥塞控制？
A：

流量控制是为避免发送方速度过快，接收方来不及处理。

拥塞控制是为了避免发送方发送过快导致网络拥塞。

两者结合，调节发送方swnd，综合考虑接收方rwnd和网络拥塞状况（cwnd）。

Q：TCP缺点
A：

内核实现、升级困难；乱序数据只能等待顺序数据到达接上，或者在缓存中等待过期；和tls等搭配的https建连时间长；网络迁移时重建连接。

  • 内核实现，升级困难
  • 收到乱序数据时，乱序数据存在缓存中，要么等顺序数据到达接上后面的乱序数据，要么在缓存中等待过期。
  • 和tls搭配的https建连时间长。
  • 网络迁移时TCP需要重建连接：TCP使用四元组标识连接，网络变动时需要重建。
Q：TCP的粘包和半粘包（拆包）和解决方法？
A：

TCP中没有消息这一说，使用tcp发送消息时 tcp会根据你发送内容的大小进行合并（粘包）或拆分（半粘包、拆包）。

  • 粘包：发送方发送多条短消息，但是接收方收到多条粘在一起的短消息。

    • 发送方:  write("hello")   write("world")
接收方:  read() 一次性读到 → "helloworld"   ← 两条消息粘在一起了！

  • 拆包：发送方发送的是一条长消息，但是接收方接收了半条消息。

    • 发送方:  write("a very very long message..............")  一次写入2000字节
接收方:  第1次 read() → 只读到前1460字节（受MSS/MTU限制，没法一次发完2000字节）
         第2次 read() → 读到剩下的540字节

常见解决方法：

  • 定义消息体消息长度|消息：开头使用一个int/long表示当前消息的长度，然后按照这个读取和拆分。

UDP

Q：什么是UDP？
A：

面向无连接的，首部8B轻量，无拥塞控制、不限制一对一的不可靠通信协议

面向无连接的：发送数据不需要建立连接。

不限制一对一：支持一对一、一对多、多对一、多对多。

无拥塞控制：网络环境和接收方不会影响发送方的发送速率。

不可靠传输：丢失不重传。

Q：如何基于UDP实现可靠传输
A：

QUIC over UDP。

  • QUIC发送多条消息时会分割为多个不同stream-id的消息并发送：比如stream1@1, stream1@2, stream2@1, stream3@2，即使stream3@2先到达，也可以在stream3的独立滑动窗口中乱序确认，直到所有的stream3@x到达与完整stream3数据包组装。

  • 无队头阻塞：quic支持不同stream的独立交付，每个stream有一个独立的滑动窗口，不会相互影响。stream5-framex的丢失不会导致后来的stream7的无法交付。

  • QUIC连接建立1RTT。QUIC中包含tls1.3，在1.5RTT内完成QUIC initial 和handshake。

    • QUIC 跑在 UDP 之上，UDP 本身无连接，不需要三次握手这种动作。QUIC 自己在应用层协议内部实现了一套"连接建立+加密协商"合并的流程，直接把 TLS 1.3 内嵌进了协议设计里（QUIC 强制使用 TLS 1.3，没有 1.2 的选项）。

    • QUIC建连 1.5RTT

      • 客户端                                    服务端
  │                                          │
  │── Initial Packet ──────────────────────▶│
  │   (ClientHello + QUIC传输参数)            │
  │                                          │
  │◀── Initial Packet + Handshake Packet ───│
  │   (ServerHello + 证书 + 加密参数         │
  │    + QUIC传输参数 + 已可用1-RTT密钥)      │
  │                                          │
  │── Handshake Packet ─────────────────────▶│
  │   (Finished)                            │
  │                                          │
  │═══ 连接建立完成，可发送应用数据 ══════════│

    • TLS1.3 1RTT建立

      • Client                                              Server
  │                                                     │
  │── ClientHello ────────────────────────────────────▶│
  │   + key_share (客户端提前算好的DH公钥参数)             │ # client_public+server_private 计算出共享密钥
  │   + supported_versions, cipher_suites                │
  │                                                     │
  │◀── ServerHello ─────────────────────────────────── │
  │   + key_share (服务端DH公钥参数)                      │ # server_public+server_private 计算出相同的共享秘钥
  │   {EncryptedExtensions}                              │
  │   {Certificate}            ← 这里开始已加密！         │
  │   {CertificateVerify}                                │
  │   {Finished}                                         │
  │                                                     │
  │── {Finished} ──────────────────────────────────────▶│
  │                                                     │
  │═══ Application Data (加密) ════════════════════════│

  • 连接复用：原来的连接基于ip port的四元组确定，现在使用统一连接id标识，网络连接变化（比如从wifi切流量）但是上下文信息不变（连接id、tls秘钥），则继续复用原TCP连接。复用时重建连接1RTT。
