DDL

MySQL 的 DDL 技术主要围绕减少表结构变更对业务读写的阻塞不断演进。

  • 早期mysql 的传统ddl：主要采用 COPY 算法，创建新表、复制旧表数据，最后替换原表。大表操作耗时长，通常因为使用shared或者exclusive的mdl锁获取方式，会阻塞业务写入/读写。
  • pt-online-schema-change（2011～2012 年逐渐成熟）：Percona 推出的外部在线 DDL 工具。创建影子表，利用 Trigger 同步原表的增量 DML，分批迁移数据后切换表，尽量避免长时间阻塞业务。
  • MySQL Online DDL（5.6，2013 年）：MySQL 原生支持 INPLACE 算法，可以在 InnoDB 内部完成部分结构变更，并通过 Online DDL Log 支持并发 DML，但并非所有 DDL 都支持。
  • 更可控的 gh-ost（2016 年，GitHub 开源）：与 pt-osc 类似，同样采用影子表迁移，但使用 Binlog 捕获增量变更，替代 Trigger，支持限流、暂停、延迟切换等能力，对生产环境更加友好。
  • 原生的 MySQL INSTANT DDL（8.0.12，2018 年）：进一步引入 INSTANT 算法，部分 DDL 只需修改元数据，无需复制数据或重建表，执行速度大幅提升；后续 8.0 版本继续扩展支持范围。

pt-osc、gh-ost 与 MySQL 原生 Online DDL 长期并存，即使是 MySQL 8.0，部分 DDL 仍需 COPY 或重建表，且原生 Online DDL 的限流、暂停与切换控制能力相对有限。

instant ddl的支持范围也有限，参考 MySQL :: MySQL 8.0 Reference Manual :: 17.12.1 Online DDL Operations。在mysql8.0的版本里面，使用ptosc或者ghost对表结构变更时并发业务读写DML的支持更好，阻塞更少。

43、OnlineDDL补充，关于 inplace 操作 为什么不需要创建临时表。

Q：Q1：MySQL Online DDL 中，INPLACE 为什么不需要创建临时表？它与 COPY 有什么区别？适用于所有 DDL 吗？INPLACE+LOCK=None的时候真的不加锁吗？
A：

INPLACE：在InnoDB内部原地执行，不创建临时表，但可能需要重建表。支持：添加/删除索引、修改列默认值等。

INPLACE 并非完全不创建临时表，也不意味着不复制数据，而是由 InnoDB 存储引擎内部完成 DDL 操作，分为两种情况：不重建的时候不需要复制原表数据，需要重建的时候和COPY类似，但是对于DDL期间的并发DML支持更好。

  1. 不重建表（No Rebuild）：例如添加普通二级索引，只需扫描聚簇索引，排序并构建新的二级索引 B+ 树，无需复制原表数据。

    1. -- inplace ddl，不加锁允许并发DML
-- 添加索引，inplace，不需要重建表
ALTER TABLE user ADD INDEX idx_name(name),
ALGORITHM=INPLACE, LOCK=NONE;

  2. 重建表（Rebuild）：例如修改字段的 NULL 属性，需要扫描原表数据，在 InnoDB 内部创建中间表并重建聚簇索引及二级索引，最后切换到新表。可能产生 #sql-ib 中间表文件，并占用接近原表大小的额外磁盘空间。

    1. -- 修改字段的null属性
-- 需要创建中间表 来修改原表的聚簇索引树，以及相关二级索引，最后原子切换
-- inplace ddl， lock = none，需重建表
ALTER TABLE user MODIFY COLUMN age INT NOT NULL,
ALGORITHM=INPLACE, LOCK=NONE;

inplace和copy的区别，一个是innodb执行的B+树构建，可以通过online ddl log记录dml变更；一个是mysql server层执行的新表创建，读取旧表数据最后原子切换，需要阻塞并发DML。

  • INPLACE：由 InnoDB 内部执行，可以采用排序、批量构建 B+ 树等优化；对于支持在线执行的操作，还可以通过 Online DDL Log 记录并应用并发 DML 变更。
  • COPY：由 MySQL Server 层主导，创建新表，逐行读取旧表数据并插入新表，最后进行表切换。通常需要阻塞并发 DML。

INPLACE 不适用于所有 DDL。 例如添加、删除普通索引、修改字段默认值通常支持 INPLACE 且无需重建表；添加删除普通列、修改字段null属性、添加主键支持 INPLACE 但需要重建表；修改字段类型（如 INT → BIGINT）通常只能使用 COPY。MySQL 8.0 参考手册#17.12.1 在线 DDL 操作 里面列出了 instant 和 inplace支持的范围：

重建 remark / affected rows
添加/删除普通索引 ✗ 不修改实际表数据
修改字段默认值 ✗ 不修改实际表数据
添加删除普通列 ✓ 需要修改聚簇索引中的每一行值
修改字段null属性（是否运行not null / null） ✓ 原因，null字段列表在一行record记录中 在记录元信息中排布（变长字段列，null值列，。。。）
添加主键支持（部分case） ✓*
修改字段类型（如 INT → BIGINT） 需要使用algorithm=COPY 修改字段类型涉及到 类型转换，每行数据的对应列的大小伸缩。
instant 虽然是innodb内部重建表，但是不支持类型转换，所以需要使用copy。
对于 涉及到 表中数据的类型转换的，需要使用copy。

inplace + lock=none的时候并非完全不加锁，onlioneddl在准备和提交表结构的时候会短暂的获取排他MDL锁，如果存在长事务，则当前online ddl 阻塞等待的时间段内，后续select 也会因为MDL锁的调度规则被阻塞，即便DDL还没有真正拿到排他锁。Mysql8.0 reference Manual#OnlineDDL和MetadataLocks一节

Q：Q2：什么是online ddl，什么是之前的ddl。
A：

之前的ddl相当于获取独占MDL锁，然后进行ddl，会阻塞后续的DML操作。

现在的online ddl是mysql 5.6 引入的功能，允许在不阻塞dml操作的情况下执行表结构变更。

Q：Q3：online ddl的性能如何判断？
A：

Mysql8.0 reference Manual#OnlineDDL Performance 一节 有提到过。

执行ddl的时候添加algorithm 可以看到受影响的行数，来确定ddl操作是inplace就地更改，还是执行表复制/重建表。

  `id` int,
  `name` varchar(255),
  `password` varchar(255),
  PRIMARY KEY (`id`)

-- 这里使用的是 INPLACE 算法。对于需要重建表的操作，InnoDB 可以在存储引擎内部重新构建聚簇索引，而 MySQL 返回的 Records 不一定统计这些内部处理的记录。

  MODIFY COLUMN `name` VARCHAR(255) NOT NULL,
  ALGORITHM=INPLACE, LOCK=NONE;
Records: 0  Duplicates: 0  Warnings: 0

-- copy 使用的 lock 至少得是shared，锁住并发写，允许并发读。
ALTER TABLE `ddl_users`
  MODIFY COLUMN `name` VARCHAR(125) NULL,
  ALGORITHM=COPY, LOCK=SHARED;

--

Q：Q：45、pt-online-schema-change和gh-ost的工作原理分别是什么？各有什么优缺点？
A：

大表的在线ddl工具，一个是percona toolkit，一个是github官方的工具。

原表的数据如何更新 分批chunk 拷贝到影子表 分批chunk 拷贝到影子表
拷贝完成后，如何切换到新表。 原子性重命名，a和a_cp，a重命名为a_bak, a_cp重命名为a。 cutover 原子性切表
支持方面
对主库影响 触发器有性能开销，会增加负载。 binlog 解析较触发器更轻量
是否需要配置binlog ✗ ✓
可控性 有限 支持动态暂停/限速/恢复
外键支持 有限支持 不支持
replaction 主从支持 一般 较好，支持多种模式的ddl。

场景 有外键、简单场景的大表在线ddl 使用。 无外键的大表在线ddl，需要主从支持。

Mysql版本变迁&升级

46、MySQL从5.7升级到8.0的主要步骤和注意事项有哪些？

升级前检查：

  1. 运行 mysql_upgrade_checker（MySQL Shell工具）： mysqlsh -- util checkForServerUpgrade root@localhost:3306，自动检测不兼容项。

    1. Note：在真正升级前，连接到旧版本 MySQL，检查数据库里有没有不兼容新版本的配置、表结构和 SQL 对象。

  2. 检查废弃功能：Query Cache已移除、 sql_mode 默认值变化、分区表必须使用InnoDB等。

    1. Query Cache 查询缓存，mysql5的功能，查询后mysql server会缓存结果。但是一旦表的数据发生修改，相关缓存就需要失效。高并发写入场景下，缓存维护与锁竞争的开销可能很大。
    2. sql_mode是一个系统变量，用来控制 MySQL 如何解析 SQL、检查数据合法性以及处理异常输入。一般生产环境下会使用严格模式。可以用select @@GLOBAL.sql_mode; @@SESSION.sql_mode来获取，旧mysql可能会支持一些新mysql中不支持的而sql mode

  3. 检查认证插件兼容性：8.0默认 caching_sha2_password，确认所有客户端支持。

    1. MySQL 的一种用户身份认证插件，负责客户端连接 MySQL 时的密码验证。
    2. mysql_native_password：MySQL 5.7 默认使用的认证方式。
    3. caching_sha2_password：MySQL 8.0 默认使用的认证方式，基于 SHA-256，支持服务端缓存认证信息，提高重复连接时的认证效率。
    4. 升级 MySQL Server 不会自动将已有用户全部切换成 caching_sha2_password 。 已有用户通常保留原来的认证插件，而新建用户使用新版本的默认认证方式。
    5. -- plugin中就是 认证插件
SELECT user, host, plugin
FROM mysql.user;

  4. 备份：执行完整的物理备份和逻辑备份。

    1. 物理备份是备份数据库底层文件，例如 InnoDB 表空间及相关文件。

      1. 通常使用支持一致性热备份的工具，例如 MySQL Enterprise Backup 或 Percona XtraBackup（注意版本兼容性）。

        优势是备份、恢复大型数据库通常更快，但对存储格式和 MySQL 版本兼容性有要求。

    2. 逻辑备份则是将数据库导出为 SQL 或其他逻辑数据格式，例如使用mysqldump。逻辑备份更容易跨版本迁移，但是大量数据需要转换、导出并重新导入，通常比较慢。

    3. 生产环境不一定必须同时做两份全量备份，关键是备份方案能支持实际恢复需求，并且已经验证过备份可恢复。如果需要按时间点恢复，还应妥善保留 Binlog。

升级方式：

  1. In-Place Upgrade 原地升级（推荐小型数据库）：停机 → 替换MySQL二进制文件 → 启动（自动执行数据字典升级）。8.0.16+不再需要手动运行 mysql_upgrade。

    1. 直接升级现有mysql server的版本，保留原来的datadir，使用新版本的mysql server启动，启动时升级数据字典和必要的系统结构。
    2. MySQL 8.0 在启动时发现旧版本的数据字典结构后，会执行必要的元数据转换。它并不是把所有业务数据导出再重新 INSERT 一遍。
    3. 优点：迁移简单，避免逻辑导出导入整库数据。
    4. 缺点：原实例需要停机，而且升级失败后的恢复比较麻烦。

  2. 逻辑导出导入：mysqldump导出5.7数据到backup.sql → 再将sql导入8.0新实例执行。最安全但最慢。

    1. 逻辑升级不代表 SQL 一定兼容。 如果导出的建表语句、存储过程或配置使用了 8.0 不再支持的语法，导入同样可能失败。但是相对的，修改也容易。

  3. 复制升级（推荐生产环境） ：搭建5.7→8.0的主从复制 → 验证数据一致性 → 切换主库。可实现接近零停机。

    1. mysql5.7 作为主库承担业务读写，mysql8通过binlog持续复制数据变更和原有数据复制。追平后验证数据一致性、兼容性和复制状态。切换时短暂停止5.7的写入，8.0追平全部已提交事务时提升为主库，proxysql切换业务连接后恢复写入。
    2. 耗时最长的全量数据迁移和增量同步，都可以在业务正常运行期间完成。 停机窗口主要集中在最后的追平、主库切换和连接迁移。
    3. 切换后 原 5.7 主库退出复制拓扑，不能直接挂到 8.0 主库下面。
    4. 问题：不是无风险的0停机，需要检查主从的gtid，binlog和replica status的状态。Mysql支持 5.7主库 8.0从库的跨版本复制，但是不支持翻过来的。对复制一致性、切换后的故障回退和路由切换的一套流程要求高

关键注意事项：

  • 不支持跨大版本升级，必须从5.7升级，不能从5.6直接升级到8.0。

    • 不支持降级：数据字典只支持5.7向8.0的转换，不支持8.0向5的转换。
    • MySQL 5.6 → 5.7 → 8.0

  • 8.0使用数据字典（Data Dictionary），升级后无法回退到5.7。

    • mysql管理数据库对象的元信息系统。对于users表，mysql还需要知道表中的列，列类型，主键、索引，属于那个数据库，使用那个存储引擎，表空间组织方式。这些信息在mysql5.7中 使用 .frm 文件等机制保存表定义信息，而 MySQL 8.0 引入了基于 InnoDB 的事务性数据字典，集中管理数据库对象的元数据。

  • GROUP BY 默认不再隐式排序，依赖此行为的SQL可能出错。

    • 5.7在fgroup by department的时候，会按照department排序。
    • 8后不会排序，结果无序。如果需要显式指定group by dptmt order by dptmt。

  • 保留字新增（如 RANK、 ROW_NUMBER、 GROUPS），检查是否与现有列名冲突。

  • utf8mb4成为默认字符集，排序规则变为 utf8mb4_0900_ai_ci，可能影响索引和比较。

note：MySQL 8.0 于 2026 年 4 月结束 Premier Support，应尽快规划升级到 8.4 LTS。

Q：Q：8.4的升级内容？
A：
  • 认证插件，默认禁用mysql_native_password，强制使用caching_sha2_password。
  • 复制相关参数重命名，完全移除旧语法：slave 该为 replica，change master to 改为 change replication source to。
  • 并行binlog复制支持。
  • 组复制简化配置。
  • 字符集默认utf8mb4。
Q：Q：8.4 LTS 和 innovation版本的区别？如何指定迁移策略？
A：

从 MySQL 8.4 开始，Oracle 正式引入 LTS（Long-Term Support） 和 Innovation 双轨发布模型。

  • LTS 版本提供更长的支持时间，适合生产环境运行。
  • Innovation 版本每个季度发不，包含最新特性但只支持到下一个版本发行。

使用select version();获取版本，使用mysql_upgrade升级mysql版本。LTS 版本只接收 bugfix 和安全补丁，不引入新功能变更，保证稳定性。

迁移策略：生产库先升级到8.4 LTS，测试开发环境可以先使用9.x的innovation版本。

Q：Q：8.4 移除或者废弃（将来移除）的功能？
A：

移除：

  • mysql_native_password 默认禁用，认证插件使用caching_sha2_password。
  • replication等语法，change master to，show slave status，skip-slave-start

废弃：

  • binlog_format参数
  • sync_master_info参数

更新所有用户的认证插件，替换所有slave/master为replica/source的配置和sql，检查客户端是否支持caching_sha2_password.

Q：Q：IOPS是什么？innodb_io_capacity控制什么？什么是O_DIRECT？innodb_flush_method 控制什么？
A：

io persecond，每秒的io次数，用于衡量磁盘 I/O 能力。SDD 远大于 HDD。

innodb_io_capacity 控制 io容量，一般HDD设置为200，提供200IOPS。用于告诉 InnoDB 可用于后台维护任务的预估 IOPS，主要影响脏页刷新、Change Buffer 合并等，默认 200；innodb_io_capacity_max 用于控制后台任务积压时更积极的 I/O 速率，但二者都不是 MySQL 整体磁盘 IOPS 的硬性上限。

linux下的innodb有两层缓存，一层是innodb进程自己的数据页缓存，一层是os page cache（linux内核管理的缓存），通过o_direct可以绕过os page cache，减少重复缓存，将更多内存留给其他用途。

o_direct不代表直接持久化buffer pool中的内容到磁盘，存储设备和文件系统元数据也有持久化要求，主要解决是否绕过os page cache。

O_DIRECT 不等于持久化，仍需考虑 fsync() 及存储设备缓存。fsync用于内核将相关文件的数据及必要元数据同步到持久存储。fsync 可以搭配 o_direct 使用。

SHOW VARIABLES LIKE 'innodb_io_capacity'; 
SHOW VARIABLES LIKE 'innodb_io_capacity_max';
SHOW VARIABLES LIKE 'innodb_flush_method'; -- fsync
SHOW VARIABLES LIKE 'innodb_flush_sync'; -- on

Q：Q：Mysql服务器出现OOM kill时？什么是OOM kill？Mysql的内存花在哪里？
A：

MySQL 内存消耗过大，Linux 内核为了避免整个系统崩溃，可能强制杀死 mysqld 进程。

排查时可以通过 Linux 的 ps、top 查看进程 RSS，通过 Performance Schema 和 sys.memory_by_thread_by_current_bytes 等视图定位内存分配，并检查 max_connections、活跃连接数及高内存 SQL。

Mysql内存花在哪里？

  • 全局共享内存

    • 包括 innodb_buffer_pool_size 数据页索引页undolog页；innodb_log_bfufer_size 对应redo log buffer；主要是buffer pool的占用。

  • 连接 / 查询 使用的内存：每个连接使用的内存。

    • MySQL 通常使用一个工作线程服务一个客户端连接（传统线程模型）。执行复杂sql时可能还会有额外申请的内存。包括 线程栈、sql排序缓冲（执行 order by的时候没有索引，需要使用filesort在内存或者临时文件中排序）、顺序扫描读取缓冲 和 随机顺序读取缓冲区。

如何定位：

  • 在linux中定位 mysqld进程的内存情况，like ps -o pid,rss,vsz,cmd -p $(pidof mysqld)。

  • 在mysql内部提供的监控表中 performance schema中，统计线程、sql、锁、内存分配等信息。

  • 在mysql内部的sys视图中定位，sys 是 Performance Schema 等底层数据提供的更容易使用的视图。

    • -- MySQL 内部已经统计到的总内存：
SELECT * FROM sys.memory_global_total;
-- 排查各个线程占用的内存。
SELECT thread_id, user, current_allocated
FROM sys.memory_by_thread_by_current_bytes
ORDER BY current_allocated DESC
LIMIT 10;
    -- thread_id 内部线程id，user 线程关联用户，currented_allocated当前已分配内存。

-- 查看各个组件占用：bunfferPool，sql执行缓冲
SELECT event_name,
       current_alloc
FROM sys.memory_global_by_current_bytes
LIMIT 10;
Q：Q：Mysql的ibdata1是什么？持续增长如何处理？共享表空间和独立表空间什么区别？
A：

ibdata1 是 InnoDB 的共享系统表空间文件，存储数据字典、undo logs（5.7 以前）、change buffer 文件、double write buffer 文件 等。

可能的持续增长原因：

  • innodb_file_per_table=off，所有表数据存在ibdata1中。默认开启，开启时每个表一个ibd文件。
  • 长事务时 undo log无法清理，ibdata中的undo log越来越大。
  • ibdata1无法缩小，唯一的缩小方法就是逻辑备份所有数据后，删除所有数据文件后，设置innodb-file-per-table为on，再重新导入逻辑备份的数据。

mysql8后，undolog存在独立表空间中，减少ibdata增长。

Q：Q：查看当前undo log的回收状态？
A：
SHOW STATUS LIKE 'Innodb_history_list_length'
-- 空

-- 2. 正确的入口在 INNODB_METRICS 里
SELECT NAME, STATUS, COUNT
FROM information_schema.INNODB_METRICS
WHERE NAME LIKE '%history%';

如果 Innodb_history_list_length 值过大，则说明 undo log链过长，此时undo log回收清理受阻。

trx_rseg_history_len 是历史链表长度大小，如果过长说明undo log回收受阻。

Q：Q：information_schema ， performance_schema, status， vairables 各是什么东西？
A：

information_schema、performance_schema 是系统数据库。

  • information_schema（元数据系统数据库） Mysql自带的系统数据库，用于查看数据库表、字段、索引等结构信息，也提供部分运行时信息。

  • performance_schema（性能监控系统数据库）：MySQL 自带的系统数据库，用于采集 SQL 执行、等待事件、锁、内存、I/O 等运行时信息。例如events_statements_summary_by_digest 可统计不同 SQL 模板的执行情况。

    • sys，performance_schema的一个视图。

  • STATUS（运行状态）：MySQL 的状态变量，反映服务器运行情况，例如 Threads_connected（当前连接数）、Questions（客户端执行的语句数）、Slow_queries（慢查询数）。

  • VARIABLES（配置参数）：MySQL 的系统变量，用于控制服务器行为，例如 max_connections（最大连接数）、innodb_buffer_pool_size（Buffer Pool 大小）。

四套不是完全独立，有时候会有交叉。

Q：Q：Mysql 如何在 kubernetes 上部署和管理？Mysql Operator for k8s是什么？为什么生产环境不建议docker部署mysql，而是k8s部署mysql？为什么有很多企业还是在 物理机或者虚拟机上部署MySQL？
A：

不是不建议用 Docker 部署 MySQL，而是生产环境中，单独使用 Docker 管理 MySQL，通常不如成熟的 K8s + Operator 方案具备完善的高可用和运维能力。

Docker 解决容器运行问题，K8s 解决容器编排问题，MySQL Operator 解决数据库集群管理问题。K8s 的主要优势是自动化运维，并非 MySQL 运行性能或数据安全性天然更好。

主要区别在于高可用、持久化、故障恢复和自动化运维。

对比 Docker/DockerCompose K8s
容器管理 手动管理或通过Compose编排 自动调度、重启、迁移
数据持久化 Volume/BindMount PV/PVC
故障恢复 可自动重启容器，跨机器恢复需额外方案 节点故障后可重新调度Pod
MySQL高可用 需要额外搭建主从复制和故障切换 可以结合MySQLOperator自动管理
扩缩容 需要自行管理数据库节点 Operator可以协调副本增减
监控运维 需要额外搭建 容易集成Prometheus、Operator等

这里需要注意三个问题：

  1. K8s 自动恢复 Pod ≠ MySQL 高可用。MySQL 主从复制、主库选举、数据一致性仍然需要 MySQL Operator 或其他高可用组件管理。
  2. K8s 不一定比 Docker 性能更好。MySQL 对磁盘 I/O 延迟比较敏感，K8s 的网络存储、存储插件可能增加开销，需要合理选择存储方案。
  3. Docker 本身不意味着数据不安全。只要正确使用 Volume、备份和高可用机制，Docker 完全可以用于生产环境。
Q：Q：为什么有很多企业还是在 物理机或者虚拟机上部署MySQL？
A：

因为 MySQL 是有状态服务，对存储性能、数据一致性和故障恢复要求较高。

K8s 虽然提供了自动化管理能力，但同时引入了网络、存储、调度和 Operator 等额外复杂性。

对于追求极致性能、稳定性的大型数据库集群，直接在物理机或虚拟机部署 MySQL，再结合 Orchestrator、ProxySQL 等组件实现高可用，同样是成熟的生产方案。

Q：Q：108、MySQL 8.4 中 InnoDB Buffer Pool 在线调整（Online Resize）的行为有何变化？
A：

innodb buffer pool之前在线调整时，大幅度缩小buffer pool，会引发比较基金的页面淘汰导致突发的大量磁盘io，同时也可能导致长时间阻塞和oom。

8.4及之后，缩小操作采用更渐进的页面淘汰策略，避免突发的大量磁盘 I/O；调整进度信息更详细，新增完成百分比和预计剩余时间。如果调整过程中检测到内存压力过大，会自动暂停并报告状态，而不是强制继续。

调整幅度建议不超过当前buffer pool size的50%，分多次进行直到完成缩小。

-- 在线调整 Buffer Pool 大小（以 chunk_size 为粒度，默认 128MB）
SET GLOBAL  innodb_buffer_pool_size =  8589934592 ;   -- 8GB
-- 监控调整进度
SHOW  STATUS LIKE 'Innodb_buffer_pool_resize_status%' ;
-- 查看详细进度
SELECT  *  FROM  performance_schema.innodb_buffer_pool_resize_status;
