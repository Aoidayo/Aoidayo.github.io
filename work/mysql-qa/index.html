按照学习顺序来组织一下Mysql的一些八股，同时也方便以后复习的时候线性阅读，减少跳跃式阅读。

Mysql整体架构

Q：Mysql的整体架构是什么？
A：

Mysql的整体架构可以分成四部分：

  • 1、客户端，负责与SQL Server建立连接，例如JDBC、MysqlShell。
  • 2、Mysql Server，负责连接管理（连接器），解析与预处理（词法分析、语法分析、语法树构建、预处理），优化器根据SQL 索引 表情况 生成执行计划，执行器根据执行计划执行sql并获得返回，响应给客户端。Server层协调binlog对数据进行归档、主从复制。
  • 3、Innodb 存储引擎层，负责真正的数据读写、事务、并发。包括buffer pool(缓存undo log、数据页、索引页、锁），redo log buffer，double write buffer。
  • 4、磁盘：最后所有数据都会落在磁盘中。（ibd表空间文件、binlog增量文件、redolog循环写文件、undolog表空间文件）
Q：一个事务中的sql如何执行？
A：

事务

BEGIN;
update accounts set balance = balance - 100 where id = 1;
update accounts set balance = balance - 100 where id = 2;
commit;

  • 客户端开启事务：客户端在数据库连接中发送begin，后续的sql都属于这个事务，直到发送commit或者rollback。

  • Server层处理每条sql：连接器收到sql后，教给解析器和预处理器处理（词法分析、语法分析、语法树构建、预处理），然后优化器根据sql和具体情况选择索引，指定执行计划，最后执行期调用innodb执行sql。

  • innodb存储引擎层读取和修改数据：通过索引定位数据页位置，如果数据页在bufferpool中直接读取，如果不在则从ibd中读取并加载到buffer pool中。根据具体情况加锁。修改前的数据添加到当前行的历史undo log版本链中，修改后更新对应的redo log 和 binlog。

    • 事务中多sql共享事务状态：事务中后执行的sql可以看见前一条sql的修改，事务提交前事务中执行的修改不会被其他事务看到。
    • 事务提交：事务提交时，通过2PC保证redo log和binlog的事务一致性，将redo log和binlog落盘，随后释放客户端持有的锁，返回对应执行结果。
    • 后台写回磁盘：事务提交时修改的脏页不需要立刻落盘，有redo log保证崩溃时的事务持久化，由后台线程将buffer pool中的脏页逐步刷盘。

如果中途执行了rollback或者事务失败，innodb会使用undo log撤销已经完成的修改。

Innodb存储结构

ibd表空间文件

每个表对应一个表空间文件ibd，ibd中的基本读写缓存单位是page，基本物理分配单位是extent，由segment分别管理不同类型的extent。

Q：为什么需要有extent？
A：

按extent进行一次性的连续物理分配，让page连续，减少随机io，提高磁盘读写效率。

在 InnoDB 中，最基础的读写单位是 Page（页，默认 16KB）。

  • 问题：如果数据库每次需要空间都只向操作系统申请 1 个 Page，即使 B+ 树叶子节点在逻辑上是用双向链表串联的，这些 Page 在磁盘上的物理位置可能散落在天南海北。当执行 SELECT * FROM t WHERE id BETWEEN 1 AND 10000; 进行范围扫描时，磁头就需要来回寻道，产生大量的随机 I/O。
  • 解决方法：InnoDB 决定“批发空间”——一次性在磁盘上划出 连续的 64 个 Page（$64 \times 16\text{ KB} = 1\text{ MB}$），这就是 Extent（区）。
  • 收益：属于同一个 Extent 的页，在物理磁盘块上是严格相邻的。执行顺序扫描时，InnoDB 可以直接触发预读机制（Read-Ahead），将连续的一整块 Extent 刷入内存缓冲区，将随机 I/O 转化为高效的顺序 I/O。
Q：为什么需要有段？
A：
隔离不同类型的数据，防止物理混杂，保障范围扫描时的顺序 I/O 性能。若只有区（Extent）：B+ 树的叶子节点（数据页）与非叶子节点（索引页）会混在同一个 Extent 中。当执行范围扫描时，连续读取会被夹杂的索引页频繁打断，导致磁盘预读失效，顺序 I/O 退化。引入段（Segment）：一棵 B+ 树被严格拆分为数据段（叶子节点）与索引段（非叶子节点）。每个段各自申请并独占独立的 Extent，确保数据段内部的所有页都是纯粹的数据页。
Q：ibd的磁盘文件视角
A：

一个 .ibd 文件在物理上就是由编号为 Extent 0、Extent 1、Extent 2、Extent 3……这样一个个 1MB 的物理块依次追加而成的。

Segment 不是磁盘上的连续大文件块，本质保存在特定的 INODE Page 中的数据段、索引段、回滚段的set，每个段中保存对应类型的extent。

  • 数据段里记录：“Extent 1、Extent 2、Extent 5 是归我使用的”。
  • 索引段里记录着：“Extent 3 是归我使用的”。

这些 Extent 在物理文件上不必相邻，只要段内部分配给叶子节点的各个 Extent 内部的 64 个页是连续的数据页，扫描时就能享受局部顺序 I/O 的红利。

Q：为什么mysql的页大小是16KB，和os的页大小不一致？
A：

常见的pgsql的页大小是8kb，mysql是16kb，更大的page size可以增加索引页的扇出，但也可能会带入无用数据，这是数据库内部对存储和缓存粒度的权衡。os页大小是虚拟内存管理的粒度，不是磁盘io时一定按页大小分割。

Linux常见的内存页是4KB,而InnoDB默认是16 KB,但它们并不需要一样。操作系统的页主要用于虚拟内存管理,而数据库页是数据库自己管理磁盘和缓存的基本单位。等于说一个16 KB 的InnoDB 页在内存里可能跨越四个4 KB的OS页框,但读磁盘时数据库是按自己的页大小组织 I/O 的,不是被4 KB硬切。页大小的选择更多是折中,页大可以减少B+树的高度、提高顺序读的局部性,但也会带来单次读写的数据更多、可能有更多无用数据被带入。所以MySQL选16 KB更多是数据库内部的权衡,而不是要去跟操作系统页对齐。两者属于不同抽象层,不需要强求一致。

InnoDB要把一个16KB的页读进Buffer Pool时,完全可以发起一次16KB的I/O请求。Linux会把这16KB的内存区域映射到多个4KB的物理内存页框,但这是内存管理的粒度,不是I/O次数被强制拆分。所以更准确的说法是:OS页大小决定的是虚拟内存的管理粒度,而InnoDB页大小决定数据库自己的存储和缓存粒度,两者不需要也通常不会相同。把“OS页大小直接等同于磁盘I/O次数”其实是不准确的。

B+树

innodb中的ibd表通过b+树组织：

  • 聚簇索引树的叶子节点中存放主键索引和完整行数据。
  • 普通索引树的叶子节点中存放索引和主键。
Q：为什么使用b+树，而不是使用AVL、红黑树或者B树？
A：

b+树的非叶子节点中只存放索引，扇出高，叶子节点中只存放数据，相邻叶子节点使用双向链表组织，范围查询和排序效率高。

AVL或者红黑树适合内存中使用，树更高，如果放在磁盘中会需要更多的磁盘io。

B树的非叶子节点中也存放数据，扇出比b+树更小；数据分散在各个节点中，单点查询、范围查询以及插入删除效率较B+树更低；磁盘io次数更多。

一行记录

Q：一行记录的存储格式？
A：

一行记录：(记录元信息 | 记录额外信息 | 字段1 |字段2 | 字段3 | ...)

  • 记录元信息：变长字段列表、null值列表、delete-mark删除标记、next-record、record-type。

    • 其中 变长字段列表、null值列表 都是逆序存，以便在同一个cpu cache line中命中排序靠前的字段值和 变长字段列表、null值列表的记录。
    • null值列表是通过逆序的bitmap进行存储。

  • 记录额外信息：row-id，trx-id, roll-ptr。

Q：什么是聚簇索引，什么是二级索引？聚簇索引和二级索引的区别？什么是回表？
A：

聚簇索引指用于建立表空间主B+树的索引，一般的如果指定PRIMARY KEY则pk作为聚簇索引列，如果没有则查找是否表字段中有unique not null列，有则作为聚簇索引，没有则默认使用记录隐藏列中的row-id建立聚簇索引B+树。

二级索引指非聚簇索引的index、key。和聚簇索引的区别在于：

  1. 可以不是unique not null，不限制唯一键
  2. 二级索引树的叶子节点存(索引值, 对应聚簇索引值)， 非叶子节点存索引值范围。
  3. 聚簇索引树的叶子节点存(聚簇索引值, 行数据)，非叶子节点存放索引值范围。

什么是回表：demo_users表有两个索引，primary key(id)和index(name)

  • select * from demo_users where id = 1; innodb在聚簇索引树中定位到id=1位置的数据后，直接返回。
  • select * from demo_users where name = 'aoi'; innodb在二级索引树中定位到name=aoi后也得到聚簇索引值，为得到完整数据，需要回表从聚簇索引树中取完整值并返回。

explain

Q：explain一般在看什么？
A：

explain参考 ((20260923105532-aminnmp “如何造数据测试explain？”))。主要看type和extra，当type标注使用了索引之后，可以看keys，possible keys，key_len具体索引。接着就是看预估扫描行数rows和索引条件后的过滤比例filtered。

rows是预估扫描的行数，filtered = 走完索引条件后，剩下的行还能通过全部条件留下来的比例（百分比估算值）。结合rows * filtered 才接近实际返回的行数。


-- 假设 demo_orders 有 idx_user_id
select * from demo_orders where user_id = 1 and status = 2;
-- status = 2 / 索引过滤后的行数 = 命中比例
-- filtered 就反映 status = 2 大概能留下多少比例，比如 20.00 表示预估只有 20% 的候选行能通过。
Q：explain的type？
A：
const 主键/唯一索引等值查一行
eq_ref JOIN 时被驱动表用主键/唯一索引等值匹配
ref 普通（非唯一）索引等值
range 索引范围扫描
index 全索引扫描（不需要读取数据行，比全表扫描好）
all 全表扫描，没有可用索引

可以在test_db中测试：

-- const：主键等值，最多返回 1 行，优化阶段就确定
-- 使用索引：demo_users 的 PRIMARY (id)
EXPLAIN SELECT * FROM demo_users WHERE id = 1;

-- eq_ref：每行驱动数据对应被驱动表唯一一行
-- 被驱动表 demo_users 使用索引：PRIMARY (id)
EXPLAIN SELECT o.id, u.username
FROM demo_orders o STRAIGHT_JOIN demo_users u ON u.id = o.user_id;

-- ref：非唯一索引等值，可能匹配多行
-- 使用索引：demo_orders 的 idx_user_id (user_id)
EXPLAIN SELECT * FROM demo_orders WHERE user_id = 1;
-- 另一个：使用 demo_orders 的 idx_status (status)
EXPLAIN SELECT * FROM demo_orders WHERE status = 1;

-- range：主键范围
-- 使用索引：demo_orders 的 PRIMARY (id)
EXPLAIN SELECT * FROM demo_orders WHERE id BETWEEN 1 AND 10;
-- 另一个：时间范围，使用 demo_orders 的 idx_created_at (created_at)
EXPLAIN SELECT * FROM demo_orders WHERE created_at > '2024-01-01 00:00:00';

-- index：扫描整棵索引树，只取索引列
-- 使用索引：demo_orders 的 idx_user_id (user_id)，且是覆盖索引
EXPLAIN SELECT user_id FROM demo_orders;

-- ALL：没有可用索引，逐行扫描整表
-- 未使用索引（pay_type 上没有索引）
EXPLAIN SELECT * FROM demo_orders WHERE pay_type = 1;
-- 另一个：demo_products 的 category_id 有 idx_category，但这里不过滤，只能全表扫
EXPLAIN SELECT * FROM demo_products;

const > eq_ref > ref > range > index > ALL越靠左越好；range 以上基本算“用上了索引”，index/ALL 属于大范围扫描，数据量大时要警惕。

EXPLAIN 里的 key 列是“实际用了哪个索引”，possible_keys 是“可选索引”。

想看更详细的可以加 EXPLAIN FORMAT=JSON ，想看实际执行的计划可以使用EXPLAIN ANALYZE （MySQL 8.0.18+）。

Q：explain的extra？
A：
extra
using index condition 索引下推
using where 使用where条件在server层过滤 using where不一定代表低效，需要结合实际的回表情况。如果回表次数少，那无所谓；如果是大量回表则需要进行优化。参考：((20260923113103-cbmr2qm “需要警惕的是using where + type=all，大量的回表加返回给server判断导致低效sql。”))
using index 覆盖索引
using filesort 文件排序，进行的排序没有可复用的索引树。
using temporary 使用临时表保存中间结果。 Mysql对查询结果做order by 或者 groupby的时候会出现这种情况，尽量避免。
Q：什么是索引下推？
A：

索引下推 ICP，index condition pushdown。将部分由server层完成的where过滤，下推至innodb层中完成。主要针对联合索引的范围查询问题，提前过滤减少回表次数。

比如select * from t_test where a>1 and b=3，无icp，当在联合索引树中查出所有a>1的后回表给聚簇索引树，最后返回给server层，server层通过b=3条件过滤后返回给client。其中回表了a>1匹配次。

如果有icp，那么在联合索引树中得到a>1的记录后，应用icp，同时过滤出b=3的再回表给聚簇索引树，取出完整记录后返回给server层。其中回表的次数只有a>1 and b=3匹配次。

Q：什么是覆盖索引？
A：

不需要回表，直接在索引树中拿到需要的数据。

-- index(name)
select name, id from t_test;
Q：什么是filesort文件排序？
A：

当select ... order by的时候没有可复用的索引树，需要在mysqld内存的sort buffer中进行排序，如果是在量太大，则在磁盘临时文件中排序后返回。

Mysql无法利用索引树直接得到有序结果时，额外做的一次排序。但是这个排序不一定真的需要走磁盘，很多时候都是在内存中排序，具体取决于数据量和sort_buffer_size的配置。

具体的，在没有可用的有序索引时，Mysql

  • 1、按某种方式（索引/全表扫描）将所有满足条件的数据取出
  • 2、在内存/磁盘的临时文件中，对这些数据按条件排序
  • 3、最后返回给客户端。

联合索引

Q：联合索引B+树长什么样？有序范围是什么？什么是最左匹配查询？联合索引查询不生效的情况？
A：

联合索引B+树也是普通的B+树，由(a, b)作为主键的索引树，a在整棵树中有序，b在相同的a中有序。

最左匹配查询：也就是联合索引生效的情况，不使用范围查询，且where条件从左到右使用联合索引中的字段a or b。

联合索引查询不生效的情况：

  • 联合索引abc，只有范围查询列和左侧列可以使用联合索引，select * from t_test where a=1 and b>2 and c=3，explain后可以发现key=idx_a_b_c，但是key_len=8，实际只使用了a和b两个字段。
  • 不按从走到右的顺序查询，比如select * from t_test where b=1 and a =2。

索引优化/失效

Q：索引优化的几种方法？
A：

索引优化的两个方向：1、优化索引空间占用，增大扇出提高索引效率。2、优化sql执行速度。

  • 覆盖索引

  • 主键设计：主键列not null，unique，id自增。id自增的方法可以使用mysql自增或者雪花id，不建议使用uuid这种全局无序完全随机的作为主键，易产生随机写入和页分裂。雪花id算法。

    • 主键列not null，主键列可以为null时无法通过主键确定是哪行数据。unique同理。

  • 索引列设置为not null。

    • server层的优化器、执行器，innodb存储引擎层，常常会忽略null列值。比如count(name) 非null的name个数, count(distinct status) 非null的status个数都会忽略null的列。

  • 前缀索引：优化长varchar的存储，增大索引节点的扇出。

  • 避免索引失效。

Q：索引失效的几种情况？
A：
  • 索引的非最左匹配查询。
  • 索引使用函数
  • 索引使用表达式计算。
  • 索引使用了隐式类型转换（触发string字段与int值的比较，string字段隐式转换为int，不可转默认0）
Q：什么是雪花id算法？
A：

64 位、分布式生成、趋势递增。生成算法依赖于机器标识和系统时钟。

雪花算法通常生成一个 64 位整数，经典结构如下：

 1 位符号位 | 41 位时间戳 | 10 位机器标识 | 12 位序列号
      0     |  当前毫秒数  | 数据中心和节点 | 毫秒内递增序号

生成 ID 时，服务先计算当前时间与自定义起始时间的毫秒差，再写入机器标识；同一节点在同一毫秒内生成的 ID，则通过递增序列号区分。各部分按位左移并组合成最终整数。

经典结构可以支持约 69 年、1024 个节点，并允许单个节点每毫秒生成 4096 个 ID。它不依赖数据库，生成结果全局唯一且趋势递增，适合分布式系统；但需要保证机器标识不重复，并处理服务器时钟回拨问题。实际项目也可以根据节点数量和并发量调整各部分的位数。

事务

Q：为什么需要事务？
A：
如果没有事务，失败的sql需要手动回滚，对数据库的并发修改可能会导致一个账号存款多扣/少扣。
Q：事务有哪些特性？
A：

ACID

  • Atomic 原子性，由MVCC版本链实现，事务失败后回滚事务中已修改的数据。

  • Consistency 一致性，由AID保证。避免出现数据不一致问题，比如AB两人一共1400元，A向B转账后两人一共只有1200元。

  • Isolation 隔离型，由MVCC版本链和锁保证。

    • 多个并发事务可以同时对一块数据进行并发一致性修改，不会因为并发事务的交叉执行导致数据的不一致性。
    • 事务执行时有自己完整的数据隔离空间，不会被其他事务的修改影响，同时也能保证对同一块数据的并发一致性修改。

  • Druable 持久型，由redo log保证数据落盘。

Q：并行事务有哪些问题？
A：

脏读（读未提交），不可重复读，幻读。

  • 脏读：A事务读到B事务未提交的数据。

  • 不可重复读：A事务前后读取的值不一样。

    • 在读提交前提下，A事务t1时刻读值100，B事务t2时刻修改值200并提交，A事务t3时刻读值300。事务执行过程中读取数据前后不一致。

  • 幻读：事务前后读取的数据数量不一致。

Q：事务隔离级别？分别解决了哪些问题？
A：

读未提交，读提交，可重复读，串行化。RU、RC、RR、Serial。

读提交解决脏读问题；可重复读解决不可重复读问题和大部分幻读问题；串行化解决了幻读问题。

Q：事务隔离级别分别是怎么实现的？
A：
  • 读未提交：不需要做事务管理，啥都不做就是读未提交。
  • 读提交：在事务开始时创建readview，事务中的每个sql执行前创建readview，避免没有读取到已提交事务的修改。
  • 可重复读：在事务开始时创建readview，之后所有sql都只能通过mvcc版本链访问事务创建时readview中记录的已提交事务对应的数据，活跃未提交和之后创建的事务对应的修改数据都不能访问，需要沿mvcc版本链向下读取。
  • 串行化：每次事务开始时加锁，提交或回滚时释放锁，严格串行化，解决幻读问题。
Q：ReadView是什么？MVCC版本链是什么？
A：

ReadView是事务开始某个时刻后，对当前活跃事务的一份mysqld进程内内存快照。只有已经提交的事务修改的数据才能访问。

MVCC版本链指的是通过记录隐藏列中的trx_id和roll_ptr维护的表记录版本链，roll_ptr指向undo表回滚段中的历史记录，trx_id表示当前记录是那个事务修改的。

Q：MVCC是什么？
A：
MVCC Multi Version Concurrent Control 多版本并发控制。MVCC解决普通查询如何无锁读取一致版本的数据。
Q：读提交如何实现的？
A：
事务中每次sql执行前创建一次readview，此时每次读sql之前都能获取到当前所有提交的事务并访问。
Q：可重复读如何实现的？
A：
事务开始时创建readview，后续的所有读sql都只能读取事务开始时创建的readview中已提交事务修改过的数据。
Q：可重复读如何解决大部分幻读问题？
A：

不太复杂的并发场景下，可以解决一部分幻读问题，比如：

  • A事务（trx_id = 51)中执行多次快照读，即使中间B事务（trx_id = 52)修改，快照读得到的数据量都是相同的：即使中间B事务修改提交，因为提交的数据trx_id>A事务id，所以A事务无法访问，所以多次快照读得到的数据量相同。
  • A事务（trx_id=51)开启时后续可能多次select的当前读，使用next-key lock锁住后续可能需要重新读取的数据行，其他事务无法修改。后续再多次select for update得到的都是相同的数据量。
Q：为什么说可重复读只解决了大部分的幻读问题，还有哪些问题没有解决？
A：

存在几种比较复杂的情况，可重复读不能解决所有幻读问题。

  • A事务（trx_id=51）t1 执行快照读，数量是50；B事务（trx_id=52）t2 向 t1 快照读的范围内insert一条数据，这个数据的 trx_id = 52，A事务无法访问；A事务 t3 执行快照读，数量依旧是50；A事务 t4 修改这条 在事务开启时本不存在的 数据，此时数据的trx_id = 51；A事务t4 执行快照读，数量变为 51，出现幻读。
  • A事务（trx_id=51）t1 执行快照读，数量是50；B 事务 （trx_id=52）t2 向 t1 快照读的范围内insert一条数据，这个数据的 trx_id = 52，A事务无法访问；A事务 t3 执行当前读，此时当前读得到的数据数量是 51, 出现幻读。

第一种是「快照读，别人insert，自己修改后再快照读」的幻读问题，第二种是「（别人修改）快照读（or 别人修改） 切 当前读」的幻读问题。

锁

MVCC 主要解决普通查询如何无锁读取一致版本，无法单独处理并发修改，因此还需要锁。

Q：表锁有哪些？
A：

  • 表锁：有X排它锁和S共享锁两种，性能最差。X表锁、S表锁。

  • MDL（meta data lock），元数据锁：非DDL上MDL读锁，DDL上MDL写锁。读写互斥。

  • Intention Lock 意向锁：分为IS表锁和IX表锁，只是占位锁，在给表中记录加X/S行记录锁之前，会上对应的IX/IS意向表锁。

    • 意向表锁之间不冲突：IS IX之间不冲突。
    • 意向表锁和S表锁、X表锁不冲突。
    • 意向锁用于快速辅助判断当前表中是否有行锁，如果有S记录锁，那么对应的就是IS锁在表上，此时不能加X表锁。如果表上的是IX锁，说明表中有X行锁，所以无法加X和S表锁。

  • 自增表锁：为了保证自增id的数据一致性，需要加自增表锁，生成自增id 插入记录后 再释放自增表锁。

  • 轻量自增表锁：性能较好的自增表锁，仅在表锁中快速生成自增id后就释放锁，insert sql执行在锁释放后执行。

    • 加锁之后生成自增id值然后释放锁，接着执行insert sql，这个insert sql可能失败，也可能并发执行。不能保证SBR format的 binlog主从复制时从库上回放sql时的数据一致性。详情可见 onenote/A3笔记/Mysql/锁/表级锁
Q：行锁有哪些？
A：

  • record lock 行级锁：锁住某条索引记录，具体是否阻塞其他事务取决于共享锁或排他锁模式。InnoDB 的行锁实际加在索引上，查询扫描的索引记录越多，锁定的范围也可能越大。

    • 读读共享、读写互斥、写写互斥。

  • gap lock 间隙锁：锁住指定索引上的间隙，防止其他事务插入。

    • 不区分 X锁、S锁。
    • 允许多个事务持有相交范围的间隙锁，比如(1,4)&(2,5)的交叉区域(2,4)。

  • next-key lock：记录锁和间隙锁的组合。

    • 唯一索引等值查询命中，对指定行加记录锁。
    • 唯一索引等值查询未命中，对可能插入该值的间隙加gap lock。
    • 普通索引等值查询命中，对已有记录和可能插入相同值的间隙加record lock 和 gap lock。

  • 插入意向锁：当插入指定位置时发现有gap lock锁着，插入意向锁进入等待状态，等待该位置的gap lock释放。gap lock释放后，插入意向锁上锁成功，后续开始插入，插入完成后再加上记录独占锁，直到事务完成。

Q：死锁是什么？
A：

事务A和事务B互相等待对方持有的锁释放，循环等待，形成死锁。

举个例子1：事务A和事务B都持有了id=5~10的gap lock，接下来事务A和B分别需要插入id=6和id=8的记录，此时因为对方持有的gap lock所以无法加插入意向锁，形成循环等待。

举个例子2：事务 A 持有记录 1 的锁并等待记录 2，事务 B 持有记录 2 的锁并等待记录 1，两个事务都无法继续执行。

Q：如何处理死锁？
A：

InnoDB 检测到死锁后，通常会选择回滚代价较小的事务并释放其持有的锁，让其他事务继续执行。业务程序需要捕获死锁错误，并对被回滚的事务进行有限次数的重试。

减少死锁的常见方法包括：让不同事务按照相同顺序获取锁、缩短事务执行时间、使用合适的索引减少锁定范围，以及避免在一个事务中一次修改过多数据。

为什么按照相同顺序获取锁可以避免死锁？ 死锁的关键条件是形成循环等待：事务 A 等待事务 B，事务 B 又等待事务 A。如果所有事务都按照主键从小到大的顺序获取锁，后来的事务只会等待前面的事务，等待关系是一条直线，无法形成环。反之，如果两个事务按照相反顺序获取锁，就可能各自持有一部分锁并等待对方，最终形成死锁。

Q：死锁如何排查，如何避免？
A：
排查可以使用 SHOW ENGINE INNODB STATUS，查看 LATEST DETECTED DEADLOCK 部分，其中会记录双方正在执行的 SQL、各自持有和等待的锁。避免死锁重点关注三件事：批量更新前按主键排序，保证所有事务按照相同顺序获取锁；将 RPC 等耗时操作移出事务，缩短持锁时间；唯一键插入冲突场景在业务语义适合时，可以使用 ON DUPLICATE KEY UPDATE 减少先查询再写入产生的竞态，但它不能彻底避免死锁。

Mysql日志

Q：一个DML update的事务过程中，记录undo log、binlog、redolog的流程？哪个地方体现WAL、2PC。
A：

分为事务执行时、事务提交时和事务提交后三个阶段。这里的binlog 和 redolog的持久化策略都是提交后就fsync。

事务执行时：现在buffer pool中定位需要修改的数据页，生成undolog并记录回滚信息（生成undolog，也就是写入undo recrod写入到undo page页，并生成redo log record到redo log buffer中），修改buffer pool中的数据页，并生成redo log。在事务执行时，binlog event也对应写入 binlog Cache中。

事务提交时：分三个阶段 Prepare，binlog写入，Commit。

  • prepare：redo log标记为prepare，写入os pageCache，按照持久化策略落盘。
  • binlog 写入 os pageCache，按照持久化策略落盘。
  • commit：redo log标记为commit，完成事务提交。

事务提交后：后台线程将脏页落盘之前，为避免脏页不能原子性写入磁盘（16kb写的时候可能一次只写了一部分，导致页损坏），先写入double write buffer，然后double write buffer触发fsync顺序写入double write file中，在确认dobulewrite落盘后 再执行脏页的落盘。

WAL，Write Ahead Logging，脏页落盘前redo log就已经持久化完成。在事务提交阶段，redo log按照持久化策略+每秒刷盘兜底执行持久化，事务结束后，脏页落盘时即使宕机，也有redo log兜底进行恢复。

2PC，2 Phase Commit，两阶段提交。保证崩溃后通过redolog恢复时 innodb的事务状态和binlog一致，简单说就是保证redo log和 binlog的一致性。

保证redolog和binlog事务一致性的不同case说明：

（1）如果在2PC的binlog写入时宕机，恢复后发现redo log的标记为prepare，那么刚才进行的事务不会恢复，binlog也没有写入或者写入了一部分，这是回滚binlog中已经写入的部分。

（2）如果在2PC的binlog写入后宕机，通过redo log恢复后的事务状态 比 binlog中记录的少，发现binlog中有完整事务，但是redolog中对应的是prepare，这里会将redolog的commit状态补上。

（3）如果在2PC的commit时宕机，redolog中残留部分prepare状态和commit状态，对照binlog中的事务状态进行恢复。

（4）在2PC的commit后宕机，此时redolog和binlog都已经落盘，恢复时也是一致的事务状态。

undo log

Q：undo log执行流程？
A：

事务开始，执行事务，修改数据前向buffer pool中写入undo log，由后台线程负责落盘，redolog保证持久化。

undo log 实现事务的原子性（失败回滚）和隔离型（MVCC创建readview后只能看见事务开始时已提交事务的修改）

Q：undo log存储？
A：
undo log 是存在表空间文件undo_001, undo_002中的，和redo log和binlog这种顺序写 增量写的文件不同。
Q：undo log版本链？什么作用？
A：
行纪录的记录头有三个属性「row_id，trx_id，roll_ptr」，roll_ptr指向前一个undo log，undo log中使用(trx_id, roll_ptr, 本行值)来串联undo log版本链（实际的存储更复杂，可以这么简单理解）。通过undo log版本链实现事务的原子性、隔离型。
Q：undo log对update 和 delete sql的特殊处理？
A：

update主键列的分别维护两个不同id的两条undo log，update常规列的正常插入undo log并写入记录；delete插入undo log链后标记记录额外信息中的delete-mark为删除，然后等待没有活跃readview依赖这个undo log时彻底删除。

对于delete sql：删除时将这条记录的额外信息中的delete-mark标记为删除，生成undo log并修改聚簇索引B+树中这条记录对应的undo log链。这条聚簇索引树中的记录在没有活跃ReadView依赖时，由purge线程清理。

对于update sql：区分修改的值是否属于主键列：

  • 不是主键列，生成undo log并写入记录，然后修改聚簇索引树中对应值。
  • 是主键列，先向这条旧id 对应的undo log链中插入新生成的undo log，然后标记这行删除，等待没有活跃readview依赖时由purge线程清理，；然后插入一条trx-id为当前事务的新记录，对应的是一条全新的undo log链（空）。
Q：undo log什么时候可以被清理？
A：

指定undo log不再被活跃的readview依赖时，后台purge线程就会判断并清理。

在RR模式下，每次事务开启都只创建一次readview，readview中包含(trx_id, m_ids, min_trx_id, max_trx_id)

  • trx_id: 当前事务id
  • m_ids: 当前活跃但没有提交的所有事务id，不一定连续。
  • min_trx_id: 当前活跃但没有提交的最小事务id
  • max_trx_id: 下一个新建事务的id。

innodb 使用 purge 线程，周期性扫描undo log，判断哪些可以回收：

  • 当不存在任何 活跃事务的readview 其可见性返回依赖这个版本的时候，可以回收。
  • 也就是 事务trx_id = T, 如果T< min_active_trx_id, 则这个事务的 undo log 不会被任何当前活跃readview获取，此时可以被purge清理。

举一个场景：ABCDE 5事务分别顺序开启，A事务启动后一直没有提交/回滚，BCD3事务提交后创建的undo log一直无法被purge清理，因为后3个事务的undo log版本>当前最小活跃事务id，事务A可能还依赖者BCD创建之前的数据，所以不能清理。

  • A事务提交后，此时可以清理ABCD四个事务的undo log，此时ABCD的undo log的版本 < E事务的trx_id。

redo log

Q：为什么需要redo log？
A：

没有redolog时脏页为落盘就宕机时会丢失数据；通过wal写redo log，宕机后恢复对应数据，保证持久性。

innodb存储引擎层 事务提交后 数据、索引、undolog 写入buffer pool的脏页，如果此时宕机，重启后无法恢复这部分脏页导致数据丢失。

添加redo log，在事务最终提交时写入redo record 到redo log buffer，按刷盘策略进行redolog的持久化，在宕机后通过redo log可以恢复这部分脏页数据。

redolog实现ACID的持久性Consistency。

Q：redolog的磁盘存储、文件组织，文件内容？
A：

redolog在磁盘中通过LSN 逻辑长序号组织文件，顺序读写，循环写。

磁盘存储：在磁盘中 mysql8.0.30之前使用ib logfile0和1交替循环读写，mysql8.0.30之后默认redolog size=100MB，通过32个3.125mb的ib_redoN进行组织。

文件内容：redolog顺序读写，每个redolog record记录(表ibd，数据页X，offset位置Y，修改Z)。

Q：redolog何时写入？何时清理？
A：

事务执行过程中脏页写入后，向redolog buffer写入redo log record；脏页落盘后 清理旧的redolog文件。

何时写入：分成写入redolog buffer，以及2PC阶段刷盘到redlog file中。

  • 写入redolog buffer：在数据页索引页在buffer pool中的脏页被修改时，生成redo log record 加入redolog buffer。
  • 2PC阶段的prepare：标记本次事务产生的redolog为prepare状态，并write+fsync到redlog文件中。（持久化策略不同 落盘时机不同：提交时不write+fsync但是每秒执行write+fsync的；提交时write但不fsync，每秒write+fsync）

何时清理：脏页落盘后清理，以及redolog file将要写满的时候。

  • 脏页落盘后，checkpoint向前推进，此时的redolog文件就可以清理对应部分了。下次写入redolog的时候，这部分就可以被覆盖写入。
  • redolog file要写满的时候，mysql阻塞，强制将部分脏页刷盘释放redolog file。
Q：缓存中的redo log buffer什么时候落盘？
A：

四种情况。

  • mysql关机时
  • 写入量 超过 redo log buffer 剩余容量的一半时，先强制刷盘。
  • 事务提交阶段，将事务产生的redo log record刷盘。
  • 每秒由后台线程进行刷盘。

binlog

Q：binlog是什么？SQL执行时如何写入和持久化的？binlog format有哪些？binlog什么作用？
A：

binlog是mysql server层维护的，记录表更改的全量日志。

SQL执行修改时，生成binlog并写入进程内存的binlog Cache中。事务提交时通过2PC保证和redo log的一致性，binlog写入os pageCache并fsync到磁盘文件中。

binlog format有 RBR，SBR和MIXED，mysql8默认使用RBR，主从复制也要求使用RBR。SBR通常会存在一些不确定性sql，在binlog回放进行主从复制的时候会导致主从不一致。

binlog什么作用：备份恢复和主从复制，通过设置binlog延迟也可以创建延迟从库。

Q：binlog和redolog的区别？
A：

逻辑/物理日志，全量/部分，作用，具体文件。

逻辑/物理日志 全量/部分 作用 具体文件
binlog 逻辑日志，记录行执行的修改，或者执行的sql。
