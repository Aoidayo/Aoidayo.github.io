按照学习顺序来组织一下Redis的一些八股，同时也方便以后复习的时候线性阅读，减少跳跃式阅读。

基本概念

Q：Redis线程模型？为什么使用单线程？为什么后面又引入多线程？多线程引入后具体是哪些多线程？
A：

单线程模型，不用考虑线程同步和加锁，高并发高性能。

Redis-Server同时处理网络IO和命令执行。redis是网络io密集型，同时写文件也涉及大量等待，将这些分开只让redis-Server主线程处理命令执行。多线程引入后具体是这些线程：redis-server负责部分网络io和命令执行，三个后台线程分别负责：

  • bio-aof-fsync：负责aof文件的刷盘。
  • bio-close-file：关闭文件线程
  • bio-lazy-free：对于大key（value大，value中元素多）的元素，使用redis-server做del耗时，使用后台线程完成内存清理。

同时redis中可以指定进行网络io的io-threads数量。

数据类型和底层结构

Q：String的底层数据结构是什么？
A：
存储int的时候，redisObject（type，embedding，ptr）的ptr中存int。字符串长度<32B的时候，使用SDS，和String的RedisObject一起分配。字符串较长时，使用RedisObject的ptr指向二次分配的SDS，SDS中存储字符串
Q：Zset的底层数据结构是什么？
A：

数据量小的时候使用ziplist/listpack，数据量大的时候使用跳表 + HashTable。

HashTable用于使用key快速定位元素，跳表用于按score排序、范围查询，支撑有序集合。

数据量小的时候使用ziplist（redis7.0之前），redis7.0之后使用listpack。

Q：ziplist、quicklist、listpack各有什么区别？
A：
ziplist是在内存中连续分配的，但是每个ziplistnode中需要存储prevlen的长度（默认1B），导致第一个位置插入一个较大的ziplistnode时（超过1B），后面都需要连续更新，开销大。quicklist主要基于双向链表，链表中的每一个元素quicklistnode都是ziplist，本质没有解决ziplist的问题。listpack的node中只存储自己的len，redis7.0后，大部分数据类型的底层数据结构都转为listpack。
Q：什么是跳表？
A：
多层有序链表，最底层就是所有数据有序排列，50%的概率上升到上一层，直到无法上升位置。search的时候从上倒下，从左到右进行，效率lgn。实现简单、不需要红黑树复杂的旋转排序。
Q：什么是整数集合（intset）？
A：
int8的数组结构，默认每个元素占用1B，可以自动向int_16、int_32升级，但是不能降级。在元素较少时作为set的底层实现之一。
Q：什么是SDS
A：
Simpe Dynamic String 简单动态字符串，底层使用buf[]数组存储，SDS字符串中字符按位置获取 / 字符串长度的获取速度为o1，前者是因为是buf数组，后者是因为SDS内部维护length长度。SDS可以存储字符串、int数组。
Q：Redis kvCache的基本结构？
A：
两个dictht哈希表，一个用于实际存储，另外一个用于在resize扩容时逐步迁移数据。
Q：Redis中数据类型和底层实现的对应关系？
A：
数据类型（value） 底层实现 数据量小的时候
string redisobject直接存，SDS统一分配（embstr），SDS二次分配（raw） /
列表 redis7.0前ziplist，redis7.0后listpack
hash hash redis7.0前ziplist，redis7.0后listpack
set hash 整数集合 intset
zset hash（o1查取） + 跳表（有序score） redis7.0之前ziplist，redis7.0后listpack
bitmap SDS（本质上string也可以存位数组，都是基于SDS）

持久化

redis中kv默认存储在内存中，宕机时使用aof日志、rdb快照或者混合持久化恢复。

Q：什么是AOF日志？redis的执行流程是什么？appendfsync的策略？
A：
AOF append only file，追加redis执行命令写入aof日志文件中，redis执行完set name aoi之后，将命令写入aofbuffer中，攒一批aofbuffer较大的时候统一执行write到pageCache中（操作系统写入文件需要先进入pageCache，如果没有aofbuffer每次都需要写入pageCache耗时）。appendfsync为always时由redis-server主线程执行命令+write后就立刻执行fsync，为everysec的时候由后台线程bio-aof-fsync每秒刷盘执行fsync，为no时有os决定使用fsync pageCache到磁盘。
Q：AOF日志过大时怎么执行重写，重写的时候如果redis有写入怎么办？
A：
AOF重写由后台线程负责，重写时根据当前数据库状态生成重建命令写入新的aof日志文件中，重写时如果有redis执行命令则先写如aof buffer和aof rewritebuffer中，aof buffer照常写入旧aof文件，aof rewritebuffer中只需要记录新执行的redis命令。重写完成时，将aof rewritebuffer中的新命令追加到新aof日志中，丢弃旧日志。如果aof rewritebuffer写满了（默认64MB），则阻塞主线程等待重写执行完成然后aof rewritebuffer刷入新aof日志。
Q：重写aof rewritebuffer记录新命令，但是重写也是扫描数据库内存状态生成的重建命令这不是一样吗？
A：
aof rewritebuffer 记录 set key1 x/y/z的变化过程，但是新生成的aof日志中可能只有set key1 z这一条。redis的原则是宁可多重复无害的命令，也不丢命令。最后追加到新生成的aof日志中会有重复的set key1 z 但是没有关系，最终状态是对的就行。当然重写的时候也不是立刻就能看到也可能刚记录完set key1 y之后就执行了新命令，使用aof rewritebuffer 避免数据丢失。
Q：为什么需要RDB快照？RDB快照的优缺点？RDB快照的执行方式？
A：

aof日志过大时 重放命令速度慢，RDB快照直接将redis内存某一时刻的全量内存数据记录，恢复时直接装入redis，速度快更高效。

RDB快照的优点：记录redis内存数据，恢复快。RDB快照的缺点：不好把控做rdb快照的频率，过快则影响redis性能，时间过长则可能数据丢失。

RDB快照的执行方式分两种：由redis-server做save，主线程阻塞写入rdb文件；fork创建子进程做bgsave做rdb快照，父进程需要修改时使用copy on write复制出来写，不阻塞主线程执行命令。

Q：什么是混合持久化？
A：

rdb恢复数据快但频繁快照影响性能、过慢则丢失数据，aof丢失数据少但是恢复数据块。结合使用rdb和aof可以在放低rdb快照频率的同时，使用aof rewrite buffer记录新执行的命令。aof日志的前半部分记录子进程的rdb快照，后半部分写入在混合持久化过程中aof rewrite buffer记录的执行的新命令。

恢复时大部分通过rdb恢复，少量增量通过aof rewritebuffer记录的新命令重放完成。

Q：AOF日志和RDB快照的异步方式都是通过创建子进程实现的异步。
A：
在主线程需要修改的时候不能修改共享内存，需要cow出来修改，如果是大key变动，则父线程redis-server 会阻塞。

过期删除与内存淘汰

Q：redis的过期删除策略是什么？
A：

惰性删除 + 定期删除。

  • 惰性删除：查询发现过期的时候，再删除。
  • 定期删除：定期清理一批过期的key。
  • 到期删除：过期了，立刻删除。cpu不友好，总是要主线程进行del。
Q：内存淘汰的策略？
A：

redis的运行内存达到max时，需要淘汰一些kv。

淘汰策略：不淘汰，淘汰设置了过期时间的，在所有kv中进行淘汰。

具体的淘汰方法有：random、ttl最大的优先淘汰，lru最近最少使用的队尾元素淘汰，lfu最近使用频次最少的淘汰。

Q：为什么lfu比lru合理点？
A：

3个元素abc，a经常使用，b最近使用过一次，c在b使用之前使用了2次。此时lru的队列是a b c，但是c的使用频次更高。在lfu中队列是 a c b，优先淘汰b。

如果b和c都使用了2次，但是b最近使用过，那么lfu就是a b c，最近最少使用的c淘汰。

缓存问题

Q：什么是缓存雪崩，如何解决？
A：

大量key在同一时间过期，大量请求达到db上并重建redis key。

不能让所有请求都负责重建key。解决方法：

  • 均匀设置key过期时间，避免同一时间过期。
  • 对于同一key，使用互斥锁进行db读取和redis更新，没有竞争到互斥锁的返回空值或者旧redis值。
  • 异步更新：对于同一过期key的并发请求，通过互斥锁进行发送key更新消息，由异步线程进行key更新。
Q：什么是Hotkey Problem，如何解决？
A：

热点key过期，大量请求打到db上。原名是缓存击穿，但是我感觉和缓存穿透类似不太好区分，所以记了下英文。

解决方法类似：核心是不让并发请求都同时访问db和更新redis。

  • 同步互斥锁更新。
  • 异步互斥锁，发消息由异步线程更新。
Q：什么是Cache Miss，如何解决？
A：

大量请求需要访问的key在redis和db中都不存在。

  • 提前校验
  • 缓存穿透key的value为null，避免穿透key执行sql。
  • 布隆过滤器：基于bitmap和多个哈希函数hashx，redis设置元素时同时使用多个hashx计算hash值存入bitmap，redis查询key时先做hashx，如果bitmap中没有对应的hash，则说明key不存在，直接返回null。如果bitmap中有对应的一串hash，只能说有可能在，此时需要先查redis后db。

双写一致性

Q：什么是Cache Aside？
A：

一种读写redis和mysql时的机制。

  • 读：查询redis，没有时查询mysql，重建redis，返回查询值。
  • 写：先改（删）redis，再写mysql。或者先写mysql，再改（删）redis。
Q：CacheAside的时候有什么问题？
A：

读写并发的时候会出现一致性问题：刚刚在mysql中写入的新值被旧的读请求重建为旧值。

A查询，B修改100为200。

  • B先写mysql，再改redis中对应的200。改完redis后A的旧请求重建redis为100。此时出现一致性问题。
  • B先删redis，再改mysql对应的100。B删redis后，A在请求时发现值不存在则查询，此时B还没有在mysql中所定行，查到100后，重建redis为100。最后B执行完成后，redis中是100，mysql中是200。此时出现双写不一致问题。

无论是先改redis再改mysql，还是先改mysql再改redis都会出现双写一致性问题。

Q：先mysql再redis 为什么比 先redis再mysql好？
A：

先mysql再redis：mysql操作时间长，所以先改mysql是正确的，改完mysql后基本能即时同步redis，双写一致性比先redis后mysql要好

  • 改mysql到结束位置 redis都是旧值100, 返回100。
  • mysql修改完 到 删redis之间，读请求查询都是100，短暂不一致。
  • 删redis后，读请求查询并重建，之后一致。
  • 也会有双写一致性问题：比如B线程在A线程写mysql和删redis之前读取age=100并阻塞，在redis删除后重建age=100, 照样不一致。

先redis再mysql：读写并发比较高的时候，删除缓存后，写入mysql之前，如果有读请求，则会导致后续的数据不一致。

  • 删除redis 到 改mysql之间：如果有并发读，会重建100出去，此时还是一致的。
  • mysql改完之后，redis还是100, 直到过期重建都是不一致的。
Q：什么是延时双删
A：

一种 Cache Aside中写策略“删redis，改mysql”在读写高并发下问题的一种补偿机制。

具体的说，在写策略的删redis和改mysql中间，如果有读请求过来重建了redis缓存，后续返回的都是旧值，不能满足数据一致性要求。

我们在这里使用”删redis，改mysql，延时删redis”可以补偿一段时间内的读请求重建redis缓存的问题，但是这里的延时不能完全解决这个问题。

假设：age=100，redis和mysql中都是100。写线程A 删除redis，更新mysql，等待500ms后再次删除redis。读线程B 查询redis，未命中后查询mysql，再将结果重建会redis。

  • B线程在第一次删除redis后读取到mysql值=100后阻塞，暂时没有写入redis，在A线程延时双删age=100后 重建age=100, 此时数据不一致。
Q：异步删除
A：

保证redis缓存能够成功删除，避免返回旧值，数据不一致。

（1）改mysql后发送mq消息+异步消费者删除：mysql删除后，向mq中添加消息；消费者监听后删除，删除成功后 移除队列；删除失败后，重试直至成功/失败到上限次数。（代码侵入性高，需要自己手动在db修改后添加mq消息，手写消费者监听队列删除缓存返回ACK等等）。

（2）使用canal订阅binlog的修改日志，向mq发送消息；消费者监听后删除缓存，成功则ACK确认处理完成，失败则重试直至成功返回ACK/失败到上限次数。（代码侵入性低）。

Q：总结「先改mysql再删redis」、「先删redis再改mysql」、「先删redis再改mysql」的补偿方案「延时双删」和「异步删除」
A：

延时双删和 MQ 异步删除本质上都是双写redis和mysql的补偿方案，它们可以缩短不一致窗口、提高删除可靠性，但无法阻止旧读请求在MQ异步删除之后重新写入缓存。整体上可以保证一段时间内的一致性，工程上想做到完全强一致很困难，有些防范不到的也属正常。

工程上尽量做最终一致性，「先删redis再改mysql」的方案的最终一致性很差，「先mysql再删redis」的效果还可以，无法防止旧读请求重建。

「先删redis再改mysql」的补偿方案有「延时双删」（这里的延时就是放前面一段时间的旧读请求，后面的异步也是）和「异步删除」，都可以达到「先mysql再删redis」的程度（这个方案兜不住前面补偿方案中预防的一段时间的读请求）。
