mysqldump和mysqlpump

Q：什么是一致性备份？

A：Mysql 数据库的事务特性 ACID的consistency 一致性，由AID一起保证。

例如：A向B转账的这个事务，转账前AB共有1000r，转账后A少200，B多200；这是数据一致性。如果转账后两人的钱少了，这是数据不一致性。

进行备份同样有这个问题，当使用 备份工具 进行备份时，如果转账事务正在进行，已经创建了转账的流水单，但是AB的钱还没有变。此时将这些全部备份下来，会得到一个数据不一致的版本「AB两者余额无变化，但是转账流水已经创建」。一致性备份得到的数据应该是「T0时刻的数据：AB旧余额，无转账流水」或者「T1时刻数据：AB新余额，有转账流水」两个状态。

一致性备份 需要 备份读取的数据来自一个共同的一致性视图。

mysqldump，单线程逻辑备份，逐表导出sql。实现逻辑类似 首先将事务隔离级别设置为可重复读 然后开启事务，利用innodb的一致性读实现备份。

mysqldump -u root -p --single-transaction --master-data=2 --routines --triggers --events --databases db1 db2  >  backup.sql
  • 备份时不影响其他事务的提交，不会改变备份事务看到的数据。此时如果开启了 转账事务，也只会读取转账事务开始前的数据版本。
  • 不会为了读取数据而长时间加表锁。
  • 基于binlog位点的主从复制集群中，备份开始前会首先短暂获取全局读锁，以同步binlog位点和一致性快照匹配，之后释放该锁，开启备份事务并导出。
  • mysqldump备份时开启事务后，之后在备份完成之前提交的事务进行的DML如何导出？不会，mysqldump只负责建立一致性备份的快照，并记录binlog位点，之后的增量DML可以使用binlog回放从T1推进到T5。

mysqlpump，多线程逻辑备份，在Mysql8.0.34被弃用，Mysql8.4移除，由mysql shell的dump utilities替代。

  • 数据一致性较弱的原因是 并行线程各自的事务快照不能简单视为一个全局快照，因此不能把单个线程的事务一致性直接等同于所有表的全局一致性。
  • 不保证表之间的一致性快照（不同线程在不同时间点读取），不适合需要严格一致性的场景。
  • 数据不一致问题已经修复了，早期 mysqlpump 的多个备份线程缺少同步点，导致备份数据不一致。之后官方的修复方法就是使用全局读锁短暂阻止写入，在锁保护期间使用多个备份线程建立一致性快照，释放全局读锁。接着各个备份线程基于快照并行导出innodb数据。
  • 后期因为功能可以被mysqldump和mysqlshell的dump utilities覆盖，就不再维护了。

mysqldump的问题：

  • 事务的MVCC一致性读无法跨跃DDL：备份事务进行时如果其他事务对将要修改的表进行ddl，备份事务备份这张表时就会报错。
  • 备份事务执行时间过长时：undo log的history list len过长无法清理

--single-transaction 的一致性保障针对 InnoDB，备份期间也应避免对相关表进行 ALTER TABLE、DROP TABLE、TRUNCATE TABLE 等 DDL 操作。MVCC 的一致性读不能跨越某些 DDL 操作，例如重建表的 ALTER TABLE。

  • MysqlReference: mysqldump, A Database Backup Program

  • 普通事务访问某张表后，MDL 通常会阻止其他事务对该表执行 DDL；但 mysqldump 的一致性快照不会提前锁住所有待备份表，因此未访问的表仍可能发生 DDL，破坏备份一致性。

  • 假设 mysqldump 要备份 A、B 两张表：

    1. T0：开启事务，创建一致性快照，但尚未访问表 B。
    2. T1：备份表 A，获取 A 的 MDL。
    3. T2：另一个连接对表 B 执行 ALTER TABLE，由于备份事务还没有访问 B，因此可能执行成功。
    4. T3：mysqldump 开始读取表 B，发现表结构已变化，可能出现 Table definition has changed，导致备份失败。

物理热备份工具 比如XtraBackUp的工作原理不同：它先复制可能处于不同时间状态的数据页，再结合 Redo 和 Undo 在准备阶段恢复出一致状态，而不是依靠一个长时间运行的 SQL 快照事务。

Percona XtraBackup

Q：XtraBackUp物理备份的基本流程？

A：

XtraBackUp 的工作原理：

  • backup：复制原始.ibd数据文件，启动后台线程追踪并复制新增的redo log（从LSN long sequence number 开始），数据拷贝完成后加全局读锁，拷贝非innodb文件和binlog位点信息，最后释放锁。

  • prepare：对备份文件进行崩溃恢复，具体的首先重放redo log，将数据页恢复到备份结束的一致性点，再通过undo log回滚该时刻尚未提交的事务的修改。

    • 如果备份期间执行的事务已经提交，此时可以通过之前的redo log向最新的lsn位置前滚，保留事务修改。
    • 如果事务没有提交，对其可能已经修改的数据通过undo log回滚数据，变更ibd数据文件，使所有数据页达到一致性状态。

  • copy-back：将备份好的文件拷贝回数据目录，重启mysql。

Q：【Mysql事务未提交 ≠ 数据页尚未落盘】xtra的prepare，如果没有提交的话，对脏页的修改也不会落盘到ibd文件中，那还需要啥undo log回滚？

A：事务中未提交的数据也能落盘：innodb采用的是steal+no-force策略。InnoDB 的脏页刷盘与事务是否提交没有直接的对应关系。未提交事务修改的数据也可能已经写入 .ibd 文件。

  • STEAL：允许未提交事务修改的脏页刷盘，如果后期事务回滚，通过undo log回滚。
  • NO-FORCE：事务提交时，不要求立即将修改的数据页刷盘，由后台线程来进行刷盘。只需要按持久化策略保证 Redo Log 持久化。

比如：

BEGIN;
-- 原来 age = 20
UPDATE user SET age = 25 WHERE id = 1;
-- 不提交
-- update 后，buffer pool中的数据页修改为25, 生成对应的undo log 和 redo log。
-- 具体的 undo log 写入buffer pool，redo log写入到redo log buffer。
-- 即使没有 commit，buffer pool中的脏数据页 也可能被刷入ibd文件
-- 如果事务最终回滚，就需要根据undo log回滚。

Q：XtraBackUp的大体流程看懂了，但是拷贝redolog 和 innodb 数据文件的时候，如果有DML操作，这个新增的dml操作在哪里进行呢？XtraBackup 复制数据文件期间，其他事务执行的 DML 如何备份？

A：DML 仍然在原 MySQL 实例上正常执行，修改 Buffer Pool 中的数据页并生成 Redo Log，脏页随后按正常机制刷盘。XtraBackup 一边复制数据文件，一边持续复制新增的 Redo Log，因此即使数据文件已经复制完成，备份期间后续发生的修改仍可通过 Redo Log 捕获。备份完成后，通过 --prepare 重放 Redo Log 恢复数据页，并利用 Undo Log 回滚一致性点尚未提交的事务，最终得到一致性备份。

percona参考：Prepare a full backup - Percona XtraBackup

Q：redolog是循环复用的，假如xtrabackup复制数据文件和追踪并复制新增redo log的速度不够快，出现redo log尚未备份就被重新覆盖的问题时，这部分新增的DML执行如何处理？

A：参考 Create a full backup - Percona XtraBackup

XtraBackup 启动独立的redo log复制线程，持续追踪新日志，尽量在MySQL 覆盖旧日志之前将其复制到备份目录。

XtraBackUp存在的问题：redolog复制线程的复制速度 « mysql写入redo的速度时，redo log产生覆盖写，xtra没能复制下来，此时备份直接失效。

  • 加入Mysql Redo log的容量为1G，Mysql每秒产生100MB redo，XtraBackup每秒复制50MB redo，xtrabackup的复制在一段时间后落后于mysql写入速度，脏页持久化redo log覆盖写了，但是被覆盖的redo log没有被 xtrabackup的 redo log复制线程复制下来。此时备份可能直接失效。

xtra 8.0.30 为解决这个问题，引入 redo-log-consumer

xtrabackup --backup \
  --register-redo-log-consumer \
  --target-dir=/backup
  1. XtraBackup 向 MySQL 注册为 Redo Log Consumer。
  2. MySQL 跟踪 XtraBackup 已经读取到的 LSN, 未被 XtraBackup 读取的 Redo Log 不允许被覆盖。
  3. 如果 redo log的 日志空间耗尽，MySQL阻塞后续写入，等待 XtraBackup消费完成后释放。

可以避免日志被提前覆盖，缺点是 备份速度跟不上时，mysql会阻塞并发dml执行，等待xtrabackup的consumer消费完成。

Q：XtraBackup如何进行增量备份？

A：命令参考Q33。

XtraBackup 基于 InnoDB 数据页的 LSN 实现增量备份。它读取上一次备份记录的 to_lsn，扫描 InnoDB 数据文件，逐页比较 Page LSN，复制 LSN 大于上次备份 to_lsn 的数据页，并结合 Redo Log 保证备份一致性。普通模式需要扫描全部数据页，存在较大的 I/O 开销；支持 Page Tracking 时，Mysql提前记录发生过变化的数据页，xtra直接定位发生变化的数据页，无需扫描全部数据页。

PITR 基于时间点的恢复

适用于 binlog开启后有binlog持续归档 且 有定期全量备份的场景。

将数据库恢复到指定时间点/某个误操作位置之前的状态。

主要流程：定位误操作的binlog位点或者时间，然后使用最近的全量备份恢复到mysql实例中，接着确认全量备份文件中的binlog位点，使用mysqlbinlog重放 全量备份文件中的binlog位点 到 误操作前的时刻或者位点 中的binlog，来恢复数据。

# 定位误操作对应的位点，或者时间点 【略】

# 恢复备份（删除原来的表及其数据，根据备份重建/插入全量备份数据，binlog重放到指定目标时间点/位点）
mysql < full_backup.sql

# 查找备份文件 类似文本中的binlog pos：CHANGE MASTER TO MASTER_LOG_FILE='mysql-bin.000005', MASTER_LOG_POS=154 
grep -i "CHANGE REPLICATION SOURCE TO" full_backup.sql

# 在数据库上执行binlog重放，将数据库中的数据恢复到目标时间点。
# 按时间点恢复（恢复到误操作前一刻）
mysqlbinlog --start-position=154 --stop-datetime= "2024-03-15 14:30:00" \
mysql-bin.000005 mysql-bin.000006  |  mysql -u root -p
# 或按位点恢复（需先用mysqlbinlog找到误操作的位点）
mysqlbinlog --start-position=154 --stop-position=28456 \
mysql-bin.000005  |  mysql -u root -p

Q：通过 mysqlbinlog 完成 PITR 后，Binlog 也恢复到目标位点了吗？

A：没有。PITR 通过重放 Binlog 恢复数据库的逻辑数据状态，但不会将目标实例的 Binlog 文件和偏移量恢复为原来的值。如果目标实例开启 Binlog，重放操作默认会生成新的 Binlog 记录；也可以使用 --disable-log-bin 禁止重复记录。原始 Binlog 位点与恢复后数据库实例的当前 Binlog 位点是两个不同的概念。

Q：PITR 是否需要从第一条 Binlog 开始重放？

A： 不需要。mysqldump/xtra 全量备份已经包含备份一致性点之前的全部数据状态，恢复时只需要从全量备份记录的 Binlog 文件和位点开始，重放后续事务直到目标恢复点的binlog位点。

如果从第一条 Binlog 开始重放，就可能重复执行已经包含在全量备份中的事务，造成数据冲突。

Q：全量备份日志中记录的binlog位点是什么？

A：是与全量备份的一致性数据状态对应的 Binlog时间 末尾位点，表示此前已经提交并包含在备份状态中的事务所对应的日志结束位置。PITR 恢复时，从该位点开始重放后续 Binlog，即可补齐全量备份之后的事务变更。

Mysql Clone Plugin

Mysql8.0.17引入的原生数据克隆插件，将一个mysql实例上的innodb数据完整clone到当前实例上，支持本地克隆和远程克隆。

-- 安装插件
INSTALL PLUGIN clone SONAME  'mysql_clone.so' ;
-- (1) 远程克隆（在目标实例上执行）
SET GLOBAL  clone_valid_donor_list =  'source_host:3306' ;
CLONE INSTANCE  FROM 'user' @ 'source_host' : 3306  IDENTIFIED  BY 'password' ;
-- (2) 本地克隆
CLONE  LOCAL DATA  DIRECTORY =  '/path/to/clone_dir' ;

具体的，基本流程是：初始化，拷贝innodb数据，页面拷贝，redo log拷贝，完成重启。

限制：

  • 克隆 会覆盖当前实例上的所有数据
  • source 和 dest 的mysql版本必须完全相同
  • ddl 在克隆期间阻塞。

生产实践

Q：逻辑备份和物理备份什么区别？生产实践中如何使用？

A：逻辑备份指导出sql语句或者csv格式数据，优点：可读性好、跨平台/跨版本兼容性好、可以选择性备份（单表、多表、整库、全部）；缺点是导出慢、恢复慢、备份期间使用一个/多个长事务来执行备份select，或者逐sql重建，可能影响性能。常见的例子是：myqsldump、mysqlshell dump utilities、mysqlpump。

物理备份直接拷贝数据文件。优点：备份和恢复的速度快（接近磁盘io速度），对线上影响小，支持增量备份；缺点是：只能恢复到同平台/同版本的mysql实例中、一般不能选择性备份。常见的工具是 xtrabackup、mysql enterprise backup、文件系统快照。

生产实践：binlog持续归档（用于pitr）+ 每天物理增量备份 + 每周逻辑/物理备份（用于跨版本跨平台恢复和验证）。方便按时间点精确恢复、快速恢复、跨平台版本恢复。

增量备份链越长，恢复时间越长。每周可以做次全量备份重置增量备份链。

Q：跨版本恢复备份中需要注意的内容？

A：跨版本无法使用物理备份，只能使用逻辑备份。

逻辑备份的sql中可能有跨版本不兼容的内容：字符集、保留字、不再支持的sql_mode，用户认证插件mysql_native_password或者caching_sha2_password。

在目标版本的空实例中导入后，验证数据完整性。

相关概念

Q：什么是LSN？为什么XtraBackup需要LSN？

A：LSN（Log Sequence Number）是 InnoDB 用于标识 Redo Log 逻辑写入位置的单调递增序列号，随着 Redo Log 的生成不断增长，即使日志文件循环复用也不会归零。InnoDB 通过 LSN 跟踪日志写入、刷盘和 Checkpoint 进度，在崩溃恢复时确定 Redo Log 的重放起点，同时 XtraBackup 也利用 LSN 确定增量备份范围。

xtra 全量备份结束时：to_lsn = 100,000; xtra 后续进行增量备份需要从 from_lsn = 100,000 开始，到redo log尾部 to_lsn = 150,000 结束，包含从LSN 100,000 到 150,000 间发生变化的数据页 就是「全量备份结束后，到我们当前增量备份这个时间点的增量数据」。

具体的：XtraBackup 基于 InnoDB 数据页的 LSN 实现增量备份。它读取上一次备份记录的 to_lsn，扫描 InnoDB 数据文件，逐页比较 Page LSN，复制 LSN 大于上次备份 to_lsn 的数据页，并结合 Redo Log 保证备份一致性。普通模式需要扫描全部数据页，存在较大的 I/O 开销；支持 Page Tracking 时，Mysql提前记录发生过变化的数据页，xtra直接定位发生变化的数据页，无需扫描全部数据页。

Q：什么是FTWRL？FTWRL在备份工具中的作用是什么？什么是备份锁Backup Lock？

FTWRL 获取全局读锁，会短暂阻塞所有DML、DDL操作，直到FTWRL释放。

FTWRL的作用？保证ReadView和记录Binlog位点的一致性，避免不一致导致的binlog位点记录不准确，PITR重放时丢失特定事务的binlog/重复重放binlog。

-- 短暂全局读锁，阻止新的写事务提交，方便确定一个一致性快照点
FLUSH TABLES WITH READ LOCK;

SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION WITH CONSISTENT SNAPSHOT; 
-- 备份事务开始，同时创建innodb的一致性快照
-- 后续select 都在备份事务中执行，读取同一个一致性快照。

SHOW BINARY LOG STATUS; -- 获取binlog位点 or gitd set。
-- mysql8.0.x的时候 使用show master status
-- -- File: mysql-bin.000005, Position: 41697720, Executed_Gtid_Set: b61b44a0-ba44-11f1-8b09-9c6b004b1e43:1-29,fa412ac4-ba44-11f1-8c59-9c6b004b1e43:1-20040

UNLOCK TABLES; -- 只释放全局读锁

-- 完成数据导出
SELECT * FROM db1.table1;
SELECT * FROM db1.table2;

COMMIT; -- 事务结束

Backup Lock 是MySQL 8.0引入的轻量级备份锁，通过 LOCK INSTANCE FOR BACKUP 获取：

LOCK INSTANCE  FOR BACKUP ;
-- 执行备份操作...
UNLOCK  INSTANCE;

不阻塞innodb表的dml（FTWRL会阻塞），阻塞DDL，对在线业务影响比FTWRL更小。

目前XtraBackup 8.0在纯InnoDB环境下自动使用Backup Lock替代FTWRL。需要 BACKUP_ADMIN 权限： GRANT BACKUP_ADMIN ON . TO 'backup_user'@'localhost'。
